# 交接文档：SWD 高速链路 + Cortex-M0+ 仿真（2026-10-26）

本文覆盖本轮工作：M0+ 真核仿真收口、`rx_early` 删除、bitstream 构建、上板测速与升频边界。
最后一节是当前仓库/板子状态和下一步建议。

## 1. 结论摘要

- **仿真**：用 ARM DesignStart Cortex-M0+ 真核做 SWD target，主功能 + 错误路径全部通过；
  修掉一个真实 bug（`ack_delay>0` 时连续 WAIT 后目标不再响应）。
- **RTL**：删除实验性 `rx_early` 采样选项（不可用，固件未使用）。
- **bitstream**：已构建并上板，时序 150 MHz FCLK（SWCLK 75 MHz）内 setup/hold 均 MET。
- **上板**：50/60/65 MHz 稳定；60 MHz 用补丁 OpenOCD 读 **3.66–3.73 MB/s**、写 **3.86–3.94 MB/s**；
  65 MHz 写 **4.03 MB/s**；20 KiB pattern 读写 **0 字节差异**。
- **边界**：68 MHz 写开始失败，70 MHz IDCODE 读错，75 MHz 连不上；≤20 MHz 低频连接失败（既有问题）。
- **再往上需要硬件改动**：给 SWDIO 加输入延迟（IDELAYE2）或第三档采样相位。

### 2.3 修掉的 bug：连续 WAIT 后 ACK 丢失

**症状**：`ack_delay>0` 时，第一笔 WAIT 正常，下一笔目标不驱动 ACK，读到 `111`/`110`（ACK=7/6）。

**根因**：`ST_ACK_EXT` 在 ACK=WAIT/FAULT 后只给一个收尾时钟就回 IDLE；目标需要一个完整
turnaround 时钟才能接受下一包头，少一拍导致包头错位。

**修复**（`fpga/rtl/swd_core.v`，已提交 `456b1b4`）：

- 新增 `ST_WTURN`（state 扩到 5 bit）；
- 仅当 **WAIT/FAULT 且 `!data_phase`** 时，在 ACK 捕获后插一个完整 turnaround 时钟，再进入解码；
- 不影响正常读写和 `data_phase` 的 WAIT 重试路径。

### 2.4 已删除：`rx_early`

- 现象：任何延时/相位组合下都读 parity 错，固件从未使用。
- 删除范围：`swd_core.v` 端口与分支、`swd_controller.v` 的 `SWD_CFG[28]` 与回读位、两个 TB、`DAP_config.h` 注释。
- 删除后快速回归（base/ack1/err0/err1/err7/phase1/turn2）全过。

### 2.5 仿真已知限制（不是 RTL bug）

- **固定采样相位**：60 MHz 下有效回环延时窗口约 12–24 ns（phase0 ≥16、phase1 ≥12），窗口外失败。
- **FAULT 未建模**：M0+ wrapper 强制 `hresp` 不产生 AP FAULT，TB 打印 `FAULT not modelled`。
- **行级 ACK 单测 `tco=20/ack_delay=1` 超时**：简易 target 模型只回 WAIT 不再给数据，RTL 的 WAIT-retry 会等数据相位；真实 M0+ 用例已覆盖。
- **低速**：FCLK/10 ≈ 6 MHz SWCLK 在仿真里也失败，与上板 ≤20 MHz 失败一致（见 §4.4）。

## 4. 上板测试

### 4.1 烧录

```powershell
python tools\run_xsct.py tools\download_dap_fpga.tcl ^
  build\xusbps_daplink_dma\O3\xusbps_daplink_dma.elf ^
  build\fpga_dma_global\system_wrapper.bit
```

脚本流程：`rst -system` → `ps7_init` → `fpga -f` → `rst -processor` → `dow` → `con`。
烧录成功后 PC 约 `0x70d0`，USB 枚举为 **CMSIS-DAP v2.1.1**，DPIDR `0x1BA01477`（F103）。

### 4.2 测速（20 KiB × 100 轮，F103 HCLK=64 MHz）

bench 脚本：`build/bench100.tcl`（先 `tools/f103_clock64.tcl` 把 HCLK 拉到 64 MHz）。

| SWCLK | nightly OpenOCD 读/写 | 补丁 OpenOCD 读/写 |
|---:|---:|---:|
| 50 MHz | 2.68 / 3.32 MB/s | 3.23 / 3.33 MB/s |
| 60 MHz | 3.05 / 3.83 MB/s | **3.66–3.73 / 3.86–3.94 MB/s** |
| 65 MHz | — | 3.73 / **4.03 MB/s** |

- 补丁 OpenOCD：`releases/openocd_pipeline_20261025/openocd.exe`（块读流水线，见 `docs/openocd流水线补丁.md`）。
- 数据完整性：20 KiB pattern 写回读 **diff_bytes = 0**。
- 说明：F103 HCLK 是易失配置，复位后恢复 HSI 8 MHz。

### 4.3 升频边界

| 请求 SWCLK | 结果 |
|---:|---|
| 60 MHz | ✅ |
| 65 MHz | ✅ |
| 68 MHz | ⚠️ IDCODE 能读对，写寄存器失败 |
| 70 MHz | ❌ IDCODE 读成 `0x1BA014FF`（稳定复现） |
| 75 MHz | ❌ `cannot read IDR`（固件接受，链路失败） |
| 80–100 MHz | ❌ 固件按 `verified_clock.json` 拒绝（`SWJ_Clock` 返回错误） |

**相位实验**：把 `SWD_CFG[17]` 强制成 early phase 后更差（60 MHz 就 IDCODE 错），
说明现有两档里 **late phase 才是对的**，68–75 MHz 需要“更晚”的采样点，当前硬件没有。

### 4.4 低频问题（既有，未修）

| 请求 SWCLK | 结果 |
|---:|---|
| 1 / 10 / 20 MHz | ❌ `cannot read IDR` |
| 25 / 30 / 40 MHz | ✅（30 MHz 偶发过一次误读，连跑 3 次正常） |

与文档里“1/10 MHz 连接未通过”一致，也与仿真里低 FCLK 失败吻合。
方向：低速档的分频/采样路径（`Set_Clock_Delay` 与 `SWD_CFG` 的 `clock_delay`/`delay_fast` 组合）。

## 6. 下一步建议

1. **bitstream 与 HEAD 对齐**：用当前 HEAD 重新跑 `build_dma.tcl`，避免 bit 落后于 `dcf048a`。
2. **打开 70–75 MHz**：给 SWDIO 输入加 `IDELAYE2`（~78 ps 步进）或第三档采样相位，
   把采样点再往后挪 1–3 ns；当前两档相位在 68 MHz 已耗尽余量。
3. **修低频（≤20 MHz）**：查 `Set_Clock_Delay` 在低速档的分频计算与 `clock_delay`/`delay_fast` 组合，
   目标 1/10 MHz 能连。
4. **固件上限**：`DAP_MAX_SWCLK_HZ` 由 `build/fpga_dma_global/verified_clock.json` 自动决定
   （`FCLK_max/2`，上限 90M）；改时序结论后要重建 bitstream 才会更新。
5. **仿真回归**：改动 `swd_core` 后至少跑
   `+errors +ack_delay=1`、`+packets`、`+packets +errors` 三组（M0+ 真核）。

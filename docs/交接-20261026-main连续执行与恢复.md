# main 连续执行优化与异常恢复

分支：`codex/main-continuous-scheduler`，工作目录：`E:/zynqlinkPRO_batch`。
起点：main `74902be`。原 main 和另一个 HFLink 工作目录没有修改。

## 最终实测

STM32F103，保持原有 96 MHz 目标时钟；不复位目标。补丁版 OpenOCD，随机
20 KiB SRAM，每个配置 6 个独立会话，每会话 300 次 dump 和 300 次 load。
每会话均校验读取内容、写入内容，以及恢复后的原始 SRAM 内容。

| SWCLK | main 读/写 MB/s | 新版读/写 MB/s | 读/写提升 |
|---|---:|---:|---:|
| 50 MHz | 3.242 / 3.349 | 3.326 / 3.417 | 2.58% / 2.02% |
| 60 MHz | 3.765 / 3.958 | 3.899 / 4.068 | 3.54% / 2.77% |

这是最后一轮同环境的新旧对照。新版前一组 60 MHz 样本为 3.987 / 4.116 MB/s；
不能把较高样本当稳定保证值。所有配置均通过数据和恢复校验。
详细数字见 `measurements/20261026-final-comparison.json`。

## 改动与耗时

1. RTL packet 引擎连续启动下一笔 SWD 事务，减少读事务之间约 2 个 FCLK 周期、
   写事务之间约 4 个周期；写数据从同步 BRAM 预取，等待与重试不消费下一笔数据。
2. 普通块读直接 DMA 到独占的 USB 响应槽，省去中间响应复制；非对齐的嵌套
   ExecuteCommands 保留私有缓冲区路径。删除应用层重复 cache flush，XUsbPs
   在发布发送描述符前仍会执行必要的 flush。很小的头部/状态使用 PIO。
3. 2–7 笔普通 Transfer 批量化实测略慢，已撤回；批量门槛保持 8。

| 环节，约 3 KiB/块 | 原测量均值 µs | 最终测量均值 µs |
|---|---:|---:|
| RTL 块读执行 | 665.82 | 651.27 |
| RTL 块写执行 | 657.70 | 631.26 |
| 完整 0x06 读处理 | 692.55 | 668.36 |
| 完整 0x06 写处理 | 686.10 | 655.33 |
| 搬运上传/下载，混合尺寸 | 8.69 / 8.44 | 7.87 / 7.65 |
| 普通块响应复制 | 3.67 | 已移除 |
| USB IN 提交，混合尺寸 | 5.19 | 3.16 |

这些统计来自不同轮次的完整工作负载，尺寸分布接近但不完全相同；子阶段可能
包含在父阶段内，队列等待和 USB 完成等待还与执行重叠，不能直接相加。
计时默认关闭，使用 `tools/dap_stage_profile.py start/stop` 显式启用。

## 异常路径修复

- USB 发送槽直到最后一个 DMA 描述符完成才释放，包括终止 ZLP；发送失败保留
  槽位重试。请求队列满时背压，避免覆盖；处理计数器回绕和执行中的会话切换。
- XUsbPs 对每个 dTD 回调，不能把首个回调等同于整个响应完成。
- SDK 重新配置 IN 描述符没有清除旧 ACTIVE 位；先停止并 flush 端点，再清理
  描述符和软件所有权。避免留下“永久无可用描述符”的状态。
- batch 引擎 busy 寄存器会在同一个时钟被 IDLE 分支覆盖；改为由状态机直接导出。
- 新增执行引擎软复位，保留 AXI、时钟配置和 BRAM，复位 core/batch/packet 状态机。
  USB 会话恢复、batch abort、packet 错误清理可以使用它；不自动重放已接受的写入。

新增 CSR：`SWD_BASE+0x4c` 为特性 `0x44500001`，`+0x50` 写 bit0 复位执行引擎，
读回复位次数。固件先检测特性，兼容旧 bit 的 USB-only 恢复。

关闭 OpenOCD 后可执行：

```powershell
python tools/dap_transport_control.py state
python tools/dap_transport_control.py recover
```

恢复会丢弃旧请求和响应，随后由主机重新执行 SWJ 连接。不会写目标 Flash，
也不拉目标 nRESET。**stock OpenOCD 不会自动调用这个恢复接口**。

## 验证范围与限制

- M0 DesignStart 目标模型：1–1023 字读写、执行中断、SWJ 重连、再次 SRAM 读写通过。
- RTL mock/AXI：同步 BRAM、WAIT 重试、部分 FAULT、奇偶校验错误、超时、两个引擎
  卡住时软复位和重启通过。M0 模型不能可靠注入 AHB FAULT，未把跳过项算作成功。
- F103 实机：packet 恢复 100 轮，其中 74 次确认引擎忙；batch 恢复 100 轮，
  其中 46 次确认忙。复位后全部可连接，恢复错误/发送错误计数均为零。
- 最终固件通过 57,600 条 16 深度排队请求，覆盖短包、ZLP、4096B 响应；
  混合小命令 1200 条和 8 种嵌套边界通过。
- 原生 C 回归覆盖 DMA 槽所有权、ZLP、发送失败、70,000 次完成及 32 位计数回绕、
  锁前复位与执行中复位。当前 Windows GCC 的 cc1 缺 DLL，可用 Clang：
  `python tools/test_dap_transport.py --cc 'C:/Program Files/LLVM/bin/clang.exe'`。

历史“多会话后持续降到 2.1 MB/s”未稳定复现，不能声称全面修好。
本次控制实验里，Vivado 运行时读/写 3.606/3.781，退出后不重载设备、也不再恢复
USB 会话，回到 3.913/4.016 MB/s；设备 RTL 执行时间几乎不变，USB 完成等待增加。
因此今后遇到降速，应同时检查主机负载、队列/引擎状态和分段计时。

输入采样窗口也仍有限：120 MHz FCLK 下显式 return_ns=8 模型会在首次 DPIDR
失败；默认 16 ns 和显式 24 ns 的 packet 测试通过。这不是本轮 packet 调度修复的内容。
当前更高频率和跨包硬件描述符队列都没有作为完成项。

## 交付文件和复现

`prebuilt/zynqlink_packet.bit` 与 `.elf` 为本轮最终配对，`SHA256SUMS` 与
`build_manifest.json` 记录校验值和构建来源。仅通过 JTAG 加载到 RAM，掉电失效。
固件 SWCLK 上限显式限制为 60 MHz。

最终 bit 的 routed 上限 138.46 MHz FCLK：setup +0.488 ns、hold +0.016 ns。
150 MHz setup=-0.068 ns，不算通过。运行测试的最高点为 120 MHz FCLK。

```powershell
python tools/deploy_dap_capture.py prebuilt/zynqlink_packet.elf prebuilt/zynqlink_packet.bit --tag final
python tools/prepare_openocd_runtime.py --exe E:/zynqlinkPRO/build/openocd-src/src/openocd.exe
python tools/benchmark_sram_optimized.py --tag repeat60 --speed 60000 --sessions 6 --loops 300 --no-reset --clock-script none --output-dir E:/zynqlinkPRO/results/optimization/repeat60 --openocd-exe E:/zynqlinkPRO_batch/build/openocd_runtime/openocd.exe --scripts E:/zynqlinkPRO/build/openocd-src/tcl
```

OpenOCD EXE 是 x64，不能混用 nightly 包的 x86 DLL。运行环境准备工具只复制到
工作目录并检查架构；不改系统 PATH 或系统 DLL。

构建继续使用分块 OOC 综合和增量实现。新工作目录可通过
`tools/prepare_ip_cache.py` 种入主线 IP 缓存，再传 `--ip-cache build/shared_ip_cache`；
本轮第二次构建只重新综合 SWD block 和顶层，避免重跑约 11 分钟的 CDMA 展开。

后续收益主要还在 SWD 时序和小命令/短操作的固定成本。大块 DMA 已只占少量时间，
如进一步做跨包连续执行，应先实现双缓冲、错误完成计数及明确的中止边界，再评估收益。

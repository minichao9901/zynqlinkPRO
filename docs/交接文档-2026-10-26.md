## 二、本轮完成的事

### 1. 定位并修复 OpenOCD `JUNK` / 连不上（关键）

现象：OpenOCD 能读出 DPIDR，随后 `dap init` 报
`SWD ack not OK @ 1 JUNK`，三种 OpenOCD（补丁版、nightly、xpack）全部一样。

定位方法：用固件的 payload trace（trace 区 `0x3F000000`）抓原始 CMSIS-DAP 字节，
看到失败请求是 5 传输的 DP 初始化批处理：

```
REQ 05 00 05 | 08 00 00 00 00 | 04 22 00 00 50 | 06 | 04 00 00 00 50 | 06
RSP 05 02 07          ← 第 3 个传输（读 CTRL/STAT）NO ACK
```

进一步二分：OpenOCD 先发 `DAP_TransferConfigure(idle=0)`，固件把 0 原样写进
`SWD_CFG[7:4]`；**idle=0 时 RTL 帧间隔不足，F103 的 DP 回 NO ACK**。
idle=1 正常，idle=2/3 也不稳（RTL 的 idle 插入位置有问题）。

修复（`DAP.c`，`DAP_TransferConfigure`）：

```c
if (idle > 15U) idle = 15U;
if (idle == 0U) idle = 1U;   /* RTL 至少需要一个空闲半周期 */
swd_write32(SWD_CFG, (cfg & ~0xF0U) | (idle << 4));
```

结果：OpenOCD 现在能 `init / halt / mdw / program`，60、64、69 MHz 都能连（75 失败）。

### 2. F103 固件版本坑

`stm32f103_rtt_speed/fw.elf`（根目录）是 **F103ZE 版**（`_estack=0x20010000`，
64 KB SRAM），烧到 CB 板（20 KB SRAM）会立刻 HardFault：
`CFSR=0x1400 (STKERR|IMPRECISERR)`、`HFSR=FORCED`、PC 停在 `Default_Handler`。

正确文件：`build-cb/fw.elf`（`_estack=0x20005000`）。

### 3. F103 主频改为 60 MHz

没有重编固件，直接用调试口改 RCC（halt 状态下 `mww`）：

```
0x40021004 = 0x00000000   ; 切回 HSI
0x40021000 = 0x00005903   ; 关 PLL
0x40021004 = 0x00370400   ; HPRE=/1, PPRE1=/2, PPRE2=/1, PLLSRC=HSE, PLLXTPRE=HSE/2, PLLMUL=×15
0x40021000 = 0x01005983   ; 开 PLL
0x40021004 = 0x00370402   ; 切到 PLL
```

读回 `RCC_CFGR=0x00370402`，确认 60 MHz 运行。

### 4. `delay_fast` 默认值

RTL 复位值原为 `4'd2`，即每个半周期 3 个 FCLK，SWCLK=FCLK/6。
本轮改为 `4'd0`（`swd_controller.v`），并在固件 `DAP_SWJ_Clock` 里显式清
`SWD_CFG[16:13]`，保证 SWCLK=FCLK/2。

> 注意：这项改动的实测效果**未能稳定复现**，见"未解决问题"。

### 5. 仿真侧（idelay 分支）

Cortex-M0+ 真实模型仿真已完成并全绿（iverilog，单次基础用例 ~4 s）：

- 修掉 WAIT/FAULT 后重跑整段 ACK 的 bug（`ST_WTURN` 回 `ST_XFER_ACK` 时 lsm 被清 0）；
- 删除无效的 `rx_early` 模式；
- `tools/run_cortexm0_regress.py` 回归矩阵：base/words64/ack1-7/errors/turn/phase/packets 全过；
- 综合通过：FCLK 上限 163.6 MHz（setup +0.111 ns）。

## 三、测量结果（F103 @ 60 MHz）

| 方式 | 读 | 写 |
|---|---|---|
| OpenOCD 60 MHz | 1.60 MB/s | 1.75 MB/s |
| OpenOCD 64 MHz | 1.61 MB/s | 1.76 MB/s |
| OpenOCD 69 MHz | 1.64 MB/s | 1.77 MB/s |
| 裸块传输（CPU halted，最好一次） | **3.61 MB/s** | **3.46 MB/s** |
| 裸块传输（CPU 跑 RTT 循环） | 1.57 MB/s | 1.66 MB/s |

结论：60/64/69 三档几乎无差别 → **瓶颈不在 SWCLK**，而在目标侧
（AP 竞争 / WAIT 重试）与主机侧（USB/PS 开销）。

## 四、未解决问题（按优先级）

1. **连发块命令后设备卡死**
   连续发几十条 `0x06` 块读后，DAP 不再响应（USB 超时），必须重新烧录
   bit/elf 才能恢复。怀疑固件响应队列/块引擎在异常路径上没复位。
   这个问题会直接打断测速。

2. **`delay_fast` / SWCLK 实际值不确定**
   改了 RTL 复位值和固件写入后，吞吐在 1.57–3.6 MB/s 之间跳，无法复现稳定的
   SWCLK=FCLK/2。需要通过 LA 抓 SWCLK/SWDIO 波形，或在 RTL 里加一个
   可读的频率计数器来确认。

3. **低速 SWJ 不可用**
   `adapter speed` ≤20 MHz 时连 DPIDR 都读不到（`cannot read IDR`）；
   `program` 只能用 50 MHz。需要修 `Set_Clock_Delay` / 低 FCLK 分频路径。

4. **OpenOCD 比裸块传输慢一倍**
   同样的 1023 字块，OpenOCD 1.6 MB/s、裸传输 3.6 MB/s。怀疑是 OpenOCD 的
   访问模式（每 4 KB 一条命令 + TransferConfigure 的 CFG 写入）或固件的
   非流水线路径导致，需要抓 USB 命令流对比。

5. **CFG 寄存器读回**
   通过 OpenOCD `mdw 0x40010008` 读到 0 是**正常**的——OpenOCD 读的是 F103 的
   地址空间，不是 Zynq PL。要看 CFG 必须用 xsct 从 PS 侧读
   （`mrd 0x40010008`），或加 vendor 命令返回。

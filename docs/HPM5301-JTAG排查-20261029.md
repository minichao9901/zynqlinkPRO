# HPM5301EVKLite JTAG 不通的原因与实板对照

日期：2026-10-29。会话来源：`Downloads/dsh-session-session-ef441056-68f0-4274-ae40-f63024bfc0c6.zip`。
排查时仓库 HEAD：`07e4b7ab6cd4a84c8d15de03eb03e09ebbe5f5da`，工作区含 DS 尚未提交的 RISC-V 改动。

## 结论：目标固件占用了自身 JTAG 引脚

用户确认 HPM5301EVKLite 正在运行 superlink/akaLink 探针固件。
该固件把自身 JTAG 所在的 PA04～PA08 切成 GPIO，用来调试外部目标。
此时把 Zynq 探针接到这组引脚，无法访问 HPM5301 自身的 TAP。
用户将目标切到 boot 模式后，在没有重新加载 Zynq bit/ELF、没有改线的情况下，原始 JTAG 扫描立即成功。

本地源码依据：

- `E:/superlinkPRO/firmware/application_5301/boards/hpm5301evklite/board.h:8`：J5 的 TDO/TDI/TCK/TMS/TRST 分别接 PA04/PA05/PA06/PA07/PA08。
- 同文件第 18 行明确说明：APP 不运行时（DFU/ISP），这组引脚才可用于调试芯片自身。
- `E:/superlinkPRO/firmware/application_5301/src/dap/DAP_config.h:791` 附近：把这些脚的 `FUNC_CTL` 写成 GPIO 的 ALT=0。
- SDK `soc/HPM5300/HPM5301/hpm_iomux.h`：这些脚的 JTAG 功能为 ALT=24。

因此不能用 TMS 复位或 TRST 脉冲修复应用程序对 IOC 的占用；重新运行同一个探针 APP 后，调试口仍会被切走。
需要调试该 APP 时，应在进入 APP 前通过 JTAG halt，或修改目标 APP 的引脚使用/初始化策略。

## 实板证据

使用现有驻留 Zynq bit/ELF，绕过 ARM DP/AP 校准和新 IDCODE CSR 打包，直接调用 `DAP_JTAG_Sequence (0x14)`。
请求 CMSIS 时钟为 1 MHz；raw sequence 有内部降速，本记录不把请求值当作实测 TCK，也不属于测速验收。

| 操作 | APP 运行时 | 用户切到 boot 后 |
|---|---|---|
| TAP reset 后默认 DR/IDCODE，连续 3 次 | `0xFFFFFFFF` | `0x1000563D`，三次一致 |
| 显式扫描 IR=1，随后读 32 位 DR | `0xFFFFFFFF` | `0x1000563D` |
| 5 位 Capture-IR | `0x1F` | `0x01` |
| IR=0x10，读取 DTMCS | `0xFFFFFFFF` | `0x00007071` |

DTMCS 解码：version=1、abits=7、dmistat=0、idle=7。
这证明当前接线、TMS/TDI 输出、TDO 输入和基本 TAP 扫描均能工作。
尚未做 DMI 寄存器访问、halt、SRAM、RTT 或 HSS 验收。

可复测脚本与原始结果：

```powershell
python tools/read_riscv_dtm.py --compare-idcode-command --output docs/hpm5301-jtag-20261029/boot-scan.json
```

结果文件：`docs/hpm5301-jtag-20261029/boot-scan.json`。
脚本只扫描 IDCODE/DTMCS；可选比较会执行 DS 的 vendor IR 设置与高层 IDCODE 命令。

## 独立存在的代码错误：新增 IDCODE 字段与 ir_after 重叠

目标进入 boot 后，这个错误仍然存在，不能把高层 `0x16` 返回的零继续解释成接线问题。

固件 `firmware/xusbps_daplink_dma/DAP/Source/JTAG_RTL.c:134` 打包：

```c
ir = len | (ir_before << 8) | (ir_after << 19) | (idcode_ir << 24);
```

而 `fpga/rtl/swd_controller.v:864` 和第 867 行同时解码：

```verilog
.ir_after(jtag_ir_config[29:19]),
.idcode_ir(jtag_ir_config[31:24]),
```

重叠范围是 `[29:24]`。单 TAP、IR 长度 5、IDCODE 指令 1 时：

```text
JTAG_IR_CONFIG = 0x01000005        // 已通过 XSCT 实际回读
ir_after = (0x01000005 >> 19) & 0x7ff = 32
```

`jtag_core.v:165`～169 会先扫 5 位指令 1，再扫 32 个 1。
对单个 5 位 TAP，最终实际装入的是 `11111`（BYPASS），随后 TDI=0 的 DR 扫描返回零。
软件 IR cache 仍记着期望值 1，它不等于目标实际接收的指令。
若用同样打包方式设置 ARM 指令 `0x0E`，同样会错误产生 448 个 ir_after 位。

同一轮实板 A/B 已确认：

```text
raw IR=1 -> IDCODE:         0x1000563D
vendor 0x8B 设置 IR=1:      8b0001
DAP_JTAG_Configure [5]:     1500
DAP_JTAG_IDCODE (0x16):     160000000000
再次 raw IR=1 -> IDCODE:    0x1000563D
```

`JTAG_ReadIDCode()` 也会在 `DAP_JTAG_Select()` 的校准失败时直接返回初始值 0。
所以 `0x16` 的全零不一定就是一次真实 DR 扫描得到的全零，更不能据此判定 TAP 已活着或接线有错。

建议 DS 将 IDCODE 指令移到独立 CSR，保留原 `ir_before/ir_after` 位域，新增完整 AXI CSR→controller→TAP 集成仿真。
现有 `tb_jtag_riscv.sv` / `tb_jtag_vexriscv.sv` 直接向 core 传 `ir_after=0`，绕过了错误的 CSR 解码，所以它们通过不能证明集成后的位域正确。
这项源码修复需要按 AGENTS.md 重建、验收并归档新的 bit/ELF 配对后再交付。

## 原会话另外两处误判依据

- `build/hpm_pins.tcl` 把 `0x94` 的 bit2 标成 A20、bit0 标成 B19，实际分别是 TDI/B19 与 TCK；TDO/A20 在 bit3。用它不能证明“TDI 驱动 0 却读回 1”。本轮按正确位域实测 manual 写 `0x100/0x104/0x102/0x106`，分别读回 `0x1A8/0x1AC/0x1AA/0x1AE`，TDI 和 TMS 均正确跟随。
- `build/hpm_bitbang_jtag.tcl` 从 Idle 发 `1,1,0` 后只到 Capture-IR，下一拍却发 TMS=1，进入 Exit1-IR，缺少进入 Shift-IR 的 TMS=0；因此该脚本并没有按注释装入 IR=1。

本次仅新增排查脚本、记录与实板结果，没有修改 RTL/Zynq 固件，没有构建或替换 bit/ELF，也没有把 DS 的未验收改动标记为已验收。
驻留产物的完整文件身份本轮未重新核验，因此这些结果不作为特定发布配对的正式验收。

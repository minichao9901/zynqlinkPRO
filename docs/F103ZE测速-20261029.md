# STM32F103ZE（scope 96 MHz）SWD / JTAG 测速与两个关键发现（2026-10-29）

目标：STM32F103ZE，Cortex-M3 r2p0（CPUID `0x411FC231`，SW-DP `0x1BA01477`，
JTAG IDCODE `0x3BA00477`，TAP 链 IR 4 + 5 两段）。目标固件为本仓库
`firmware/target/stm32f103_scope`，按 `-Board ze -CpuMhz 96` 构建并在板上跑起来。

本文记录三件事：**JTAG 为什么一开始"怎么扫都是 0"、AP TAR 到底是 1 KiB 还是 4 KiB 回绕、
以及这块板 SWD/JTAG 的完整测速**。

## 2. 关键发现 A：JTAG 被**目标固件**关掉了（AFIO_MAPR.SWJ_CFG）

### 现象

`DAP_JTAG_IDCODE` 在所有档位（250 kHz～5 MHz）、所有链配置（`[4]`/`[5]`/`[4,5]`/`[5,4]`/`[8]`）
都返回 `16 00 00 00 00 00`，但：

- 时钟观察器 `0xF8` 显示 pad 沿数 == intended（一次 IDCODE 50 个 TCK，累计 238/238），`0xFC` 异常位为 0；
- 缓存 IR 寄存器 `0x9C` 停在 **`0x0A`（DPACC）**，而不是 IDCODE 的 `0x0E`；
- 同一块板 SWD 完全正常（`DPIDR=0x1BA01477`、`CPUID=0x411FC231`）。

`0x9C=0x0A` 说明 IDCODE 命令**根本没走到装载 IR** 就退出了：固件在
`DAP_JTAG_Select()` 里先用一次 AP 读 CPUID 做校准，校准失败就直接返回。

### 根因

用 SWD 读 `AFIO_MAPR = 0x40010004`，得到 **`0x04000000`**，即 `SWJ_CFG=100`
（JTAG-DP 与 SW-DP 都关闭）。写回 `SWJ_CFG=000` 后，**下一次 IDCODE 立即返回
`0x3BA00477`，`0x9C` 也变成 `0x0E`**。

STM32F1 复位后 JTAG 默认是开的，但固件可以写 `AFIO_MAPR.SWJ_CFG` 把 JTAG（甚至 SWD）
关掉——常见目的就是把 PA15/PB3/PB4 释放成普通 GPIO。这种关闭状态只有系统复位
（或再次写 `SWJ_CFG=000`）能恢复。

两块 F103ZE 都是同一现象；而 F103CB 那块固件没动 `SWJ_CFG`，所以 JTAG 一直正常——
这也是之前"换一块板就好了"的原因。

### 修复

`firmware/target/stm32f103_scope/src/main.c` 在打开 AFIO 时钟后显式写：

```c
AFIO_MAPR = (AFIO_MAPR & ~AFIO_MAPR_SWJ_CFG_MASK) | AFIO_MAPR_SWJ_CFG_FULL;   /* SWJ_CFG=000 */
```

并已重新构建、烧录（`program verify` 通过）、上板复核 JTAG IDCODE。

> 对**没有 SWD 可用**的板子，进 JTAG 只能靠 connect-under-reset：先按住 nRESET 再扫 TAP。
> 本探针的 nRESET 暂未引出（用户板上是 E11，当前 bitstream 未约束），已列入后续改动。

## 3. 关键发现 B：AP TAR 回绕是 **4 KiB**，不是 1 KiB

方法：在 `0x20008000` 写 8 KiB 逐字递增图案，然后从 4 KiB 页内不同偏移起读 1023 字
（DAP 单块上限 4096 字节响应），看序列在哪里跳回。

| 起读偏移 | 读到 word 255/256 | 说明 |
| --- | --- | --- |
| 页内 +0x000 | 255 / 256 | 1 KiB 边界连续 |
| 页内 +0x400 | 511 / 512 | 2 KiB 边界连续 |
| 页内 +0xC00 | **1023 / 0** | 在 4 KiB 页边界回绕 |

即：`TAR` 自动增址在 **4 KiB 页**内回绕。旧工具按 1 KiB 分块是"保守但浪费"——
多发了约 4 倍的块命令。

同时确认 DAP 包长限制（`DAP_PACKET_SIZE = 4096`）：

| 方向 | 头部 | 单块最大载荷 | 字数 |
| --- | ---: | ---: | ---: |
| 块读响应 | 4 B | 4092 B | 1023 |
| 块写请求 | 5 B | 4088 B | 1022 |

`tools/test_probe_board.py` 的 `Memory` 已改为同时满足两个限制：
`chunk = min(remaining, 上限, 4 KiB 页剩余)`。验证：20 KiB 写/读 20 KiB 全字节一致、
恢复一致；1/10/30/60 MHz JTAG 下 4 KiB 写读校验通过。

## 4. SWD 验收（F103ZE，每点 3 轮 4 KiB 随机写读 + 恢复）

## 5. JTAG 验收（链 `[4,5]`，每点 3 轮 4 KiB 随机写读 + 恢复）

| 请求 | 实际 TCK | 采样模式 | 结果 |
| ---: | ---: | ---: | --- |
| 250 kHz / 1 MHz / 10 MHz / 20 MHz / 25 MHz | 同值 | 0 | PASS |
| 30 MHz | 30.0 MHz | 17 | 扫描时 1 次 `SRAM byte mismatch`，随后 3 次重复 3/3 PASS（**偶发**） |

## 6. 吞吐（512 字块、流水深度 32、每点 3 次取中位）

| 传输 | 请求 | 目标状态 | 读 MB/s | 写 MB/s |
| --- | ---: | --- | ---: | ---: |
| SWD | 30 MHz | halt | 2.33 | 2.33 |
| SWD | 60 MHz | halt | **4.82** | **4.74** |
| SWD | 60 MHz | running | 4.83 | 4.75 |
| JTAG | 45 MHz | halt | 1.82 | 1.81 |
| JTAG | 60 MHz | halt | **2.42** | **2.40** |
| JTAG | 60 MHz | running | 2.42 | 2.40 |

- F103 目标主频只有 96 MHz、且固件只是 SysTick + 少量变量更新，**halt 与 running 没有差别**
  （和 H743 那种 480 MHz 核狂读 AXI SRAM、运行态掉一半完全不同）。
- JTAG 60 MHz 的 2.4 MB/s 明显低于 SWD 的 4.8 MB/s：JTAG 每个字要 35 位 DR 扫描 + TAP 状态
  开销，而且这条链上还有 5 位 boundary-scan 旁路位。

30 s 连续 soak（SWD 60 MHz、2 KiB 块、深度 32、halt）：**0 错误**，读中位 4.83（最低 4.76）、
写中位 4.75（最低 4.57），末次回读与 SRAM 恢复一致。

## 6.1 50 MHz / 60 MHz 三项汇总（本板）

**① 最大块吞吐**（512 字块、深度 32、目标 halt、3 次中位）

| 线速 | SWD 读 / 写 | JTAG 读 / 写 |
| ---: | ---: | ---: |
| 50 MHz | 4.03 / 3.98 MB/s | 2.02 / 2.01 MB/s |
| 60 MHz | **4.82 / 4.74 MB/s** | **2.42 / 2.40 MB/s** |

**② RTT→CDC 转发**（RAM 生产者，8 KiB 环，chunk 2048，3 s 窗口，2 次）

| 线速 | 主机 MB/s | 探针计数 MB/s | 完整性 |
| ---: | ---: | ---: | --- |
| 50 MHz | 3.99～4.00 | 4.01 | 全发布字节收到、u32 序列连续、0 错误 |
| 60 MHz | **4.78～4.80** | 4.80 | 同上 |

- chunk 1024 时 50 MHz 只有 3.86、60 MHz 4.63～4.65；**2048 是最优点**。
- 这是目前测过的最高 RTT 转发速度（H743 上是 4.23）。

**③ HSS 采样率与跳点率**（SWD，24 MHz tick，跳点率 = skipped/(produced+skipped)）

| 线速 | 1 变量（4 B/样本） | 8 变量（32 B/样本） |
| ---: | --- | --- |
| 50 MHz | 1,000,000 Hz（period 24，接口下限），3 次复核 3×0% | 101,695 Hz（period 236），3 次复核 0% / 0% / 0.31% |
| 60 MHz | 1,000,000 Hz（period 24），3 次复核 0% / 1.05% / 0% | **121,827 Hz（period 197），3 次复核 3×0%** |

- 1 变量被 24-tick（1 MHz）接口下限卡住，链路本身还能更快；1 MHz 时 FIFO 只有 16 个样本
  （16 µs 深），主机 USB 抖动会带来偶发 ~1% 跳点，不是 SWD 误码。
- 8 变量在 60 MHz 的拐点很陡：period 197 = 121.8 kHz 零跳点；再快一档到 period 195
  立刻变成 68.5% 跳点（服务时间略超周期 → 隔拍丢弃）。
- 50/60 MHz 两档的 8 变量上限比 = 121.8/101.7 ≈ 1.20，和时钟比 60/50 = 1.2 一致。

## 6.2 JTAG 模式下的 RTT 与 HSS（同板同固件，链 `[4,5]`）

**RTT→CDC 转发**（chunk 2048，3 s 窗口，2 次，0 错误）

| 线速 | 主机 MB/s | 探针计数 MB/s | 完整性 |
| ---: | ---: | ---: | --- |
| 50 MHz | 1.99 | 2.00 | 全发布字节收到、序列连续 |
| 60 MHz | **2.39～2.40** | 2.39 | 同上 |

JTAG 的 RTT 上限 ≈ SWD 的一半（4.80 → 2.40 MB/s），和两种传输每字所需位数比例一致：
JTAG 每个 AP 读要 DPACC+APACC 两次 35 位 DR 扫描 + TAP 状态开销，SWD 是 46 位一包。

**HSS 采样率与跳点率**（24 MHz tick）

| 线速 | 1 变量 | 8 变量 |
| ---: | --- | --- |
| 50 MHz | 零跳点 269,663 Hz（period 89）<br>峰值 396,825 Hz（period 60，0.79% 跳点） | 零跳点 **45,369 Hz**（period 529）<br>再快一档 527 → 6.25% 跳点 |
| 60 MHz | 零跳点 324,324 Hz（period 74）<br>峰值 595,239 Hz（period 40，0.79% 跳点） | 零跳点 **54,299 Hz**（period 442）<br>峰值 54,745 Hz（period 411，6.25% 跳点） |

- JTAG 的 HSS 上限比 SWD 低约 2.2～2.4 倍（8 变量 45.4/54.3 kHz 对 101.7/121.8 kHz），
  1 变量也不再被 24-tick 接口下限卡住，说明瓶颈已经从 API 下限变成链路本身。
- 拐点形状和 SWD 一样是"台阶"：零跳点 → 6.25% → 50% → 66%…，每档丢固定比例的样本。
- **关于 `all_frames_byte_exact=false`（已查清，不是数据错）**：这个字段名是历史误名。
  `HssReader.validate_values()` 对**每一个 kind=2 数据帧**都做 `assert data == expected*n` 的
  逐帧字节比较，任何不一致会直接抛异常；而 `all_frames_byte_exact` 实际取的是
  `not control_sequence_errors`，后者只记录"重复的统计帧（kind=3，序号相同）"——是控制面
  重发，不承载采样数据。名字来自 `tools/benchmark_probe_stream.py`（提交 `381f645`），
  被 HSS 扫描工具沿用。
- 复核结果（JTAG 60 MHz、8 变量、period 441 附近）：每行逐帧校验 **4,184～11,720 个数据帧**
  全字节一致，`stat_duplicate_frames` 只有 0～1（出现在每轮起始的统计帧重发）。所以
  8 变量 JTAG 的数字是有效的，**没有采样数据损坏**。工具已改为显式输出
  `data_frames_verified` 与 `stat_duplicate_frames` 两个字段，旧字段保留兼容。

## 6.3 JTAG 扫描 idle cycles 的 A/B（60 MHz）

固件在 `PORT_JTAG_SETUP()` 里把 `SWD_CFG[7:4]`（idle_cycles）固定写成 1，**不随频率自适应**；
自适应的只有 `calibrate()` 的采样模式 `{0,1,17,16}` 和 FCLK 降档兜底。

为确认 1 是否最优，在 60 MHz 下做 A/B：每次重新 `DAP_Connect`（固件会把 SWD_CFG 复位成 `0x11`），
再从 PS 侧只改 `[7:4]` 字段，然后跑同一套 2 KiB×256 块、深度 32 的流水。

| idle | SWD_CFG | 读 MB/s | 写 MB/s | 每扫描时钟 |
| ---: | --- | ---: | ---: | ---: |
| **1** | `0x00000011` | **2.418** | **2.394** | 42 |
| 2 | `0x00000021` | 2.370 | 2.349 | 43 |
| 3 | `0x00000031` | 2.325 | 2.300 | 44 |

- **idle=1 最快**，符合结构下限：一次 35 位 DR 扫描 = 4 拍导航 + 35 拍数据 + 2 拍退出 + 1 拍 idle
  = 42 拍 TCK；每多加 1 拍约损失 2%（42/43/44 → 2.418/2.370/2.325，实测与线性预测一致）。
- idle=0 不成立：扫描必须回到 Run-Test/Idle，否则下一次 IR 扫描会从 Update-DR 走错分支。
- 所以 60 MHz 下 JTAG 的 2.42 MB/s 与 idle 无关，瓶颈是每次 AP 访问要两次 35 位 DR 扫描。
- 测量注意：本轮先跑的对照脚本没有做"批量发请求再批量收响应"，得到 2.03 MB/s 的假低值；
  改成和 `h743_peak.py` 相同的流水（先发 32 个请求再收 32 个响应）后与峰值一致。

## 7. 复现

```powershell
# 目标固件（96 MHz / ZE）
cd firmware\target\stm32f103_scope; pwsh -File build.ps1

# 烧录（SWD，探针 DAP）
openocd -s <openocd>\scripts -f interface/cmsis-dap.cfg -c "transport select swd" `
  -c "adapter speed 2000" -f target/stm32f1x.cfg -c "init" -c "halt" `
  -c "cortex_m reset_config sysresetreq" `
  -c "program firmware/target/stm32f103_scope/build/fw.elf verify" -c "reset run" -c "shutdown"

# SWD 扫描
python tools\test_h743_board.py --transport swd --address 0x20008000 `
  --speeds 250,500,1000,2000,5000,10000,20000,25000,30000,35000,40000,45000,50000,55000,60000 `
  --bench-speeds 10000,30000,50000,60000 --bench-loops 512 --depth 32 `
  --output results\f103ze\sweep_swd.json

# JTAG 扫描（注意 --jtag-ir 4,5）
python tools\test_h743_board.py --transport jtag --jtag-ir 4,5 --address 0x20008000 `
  --speeds 250,1000,10000,20000,25000,30000,35000,40000,45000,50000,60000 `
  --bench-speeds 10000,30000,45000,60000 --bench-loops 512 --depth 32 `
  --output results\f103ze\sweep_jtag.json

```

## 8. 结论

1. **JTAG 在 F103ZE 上完全可用**：IDCODE/CPUID/4 KiB 写读全过，1 MHz～60 MHz 都通
   （30 MHz 有一次偶发失败，重复 3 次未复现）。
2. **"JTAG 全 0" 的根因是目标固件把 `AFIO_MAPR.SWJ_CFG` 设成 100**，与探针/接线无关；
   新 scope 固件已显式保持 `SWJ_CFG=000`。
3. **TAR 是 4 KiB 回绕 + 4096 字节包长**，工具分块已按两者同时约束，20 KiB 双向校验通过。
4. 吞吐：SWD 60 MHz 读 4.82 / 写 4.74 MB/s；JTAG 60 MHz 读 2.42 / 写 2.40 MB/s；
   目标 halt/running 无差异。

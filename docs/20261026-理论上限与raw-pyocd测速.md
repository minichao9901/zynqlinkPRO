# SWD 理论上限、raw 和 pyOCD 0.46.0 实测

同一 F103，RCC CR=`0x03035983`、CFGR=`0x0029250a`，保持现有 HSE×12=96MHz。
本轮没有改 bit/ELF、没有重新综合、没有复位目标或编程 Flash。
单位全部为十进制 MB/s（1 MB=1,000,000 bytes）。分支 `codex/main-continuous-scheduler`。

## 理论上限

普通、成功、无 WAIT 的 32-bit SWD 事务：请求8 + 请求后turnaround1 + ACK3 +
数据32 + parity1 + 另一个方向turnaround1 = **46个SWCLK**。
因此有效数据上限 `4×f_SWCLK/46`，并不是4MB/s。
AP posted read 的末尾 RDBUFF、写完成检查、TAR/SELECT/CSW、空闲时钟和 WAIT 均会再扣除。

| 层次 | 50MHz，读/写 MB/s | 60MHz，读/写 MB/s |
|---|---:|---:|
| SWD 协议，无 idle，渐近上限 | 4.348 / 4.348 | 5.217 / 5.217 |
| 每事务1个 idle，渐近上限 | 4.255 / 4.255 | 5.106 / 5.106 |
| 当前 RTL，idle=1，1022字/块，含最终RDBUFF | 3.956 / 4.077 | 4.747 / 4.893 |
| 当前 RTL 若能可靠使用 idle=0，相同仿真条件 | 4.162 / 4.206 | 4.995 / 5.047 |

最后两行来自新仿真 `tb_packet_wire_budget.sv`：实际 packet FSM + 实际 swd_core +
带输出延迟的串行目标，不使用瞬间完成的 core mock；检查 ACK、奇偶校验和启动次数。
idle=1时1022字：读103331个FCLK、写100267个FCLK，均有1023次SWD事务；
公式为 `有效字节数×(2×SWCLK)/FCLK周期数`。不包括PS、DMA、USB或目标WAIT。

**idle=0只是仿真预算，不是本轮实机通过项。**现有固件仍将请求idle=0钳为1，
因为此前初始化有失败。若要移除它，必须解决原问题后完整回归。

当前读路径每字比写路径约多3个FCLK，说明读写不对称部分已经存在于RTL调度和
读后处理；不能全部归因于USB或目标时钟。

## 实机 raw

新工具 `tools/raw.py`，实际发送0x06，1022字=4088B有效数据，16条命令排队。
每个频率3轮，每轮1000次读和1000次写，读取逐包检查内容，写后检查整窗口，
最终恢复并验证原SRAM。表中按总字节/总耗时汇总，未选最高样本。

| 模式 | 50MHz 读/写 MB/s | 60MHz 读/写 MB/s |
|---|---:|---:|
| raw，一发一收 | 3.180 / 3.185 | 3.674 / 3.678 |
| raw，16深度流水 | **3.796 / 3.859** | **4.532 / 4.603** |
| 上轮OpenOCD，20KiB线性内存 | 3.326 / 3.417 | 3.899 / 4.068 |

raw流水已达到当前RTL仿真上限约94–96%。相对于46周期协议上限，仍只有约87–89%，
所以优化应区分“当前RTL之外约4–6%的开销”和“RTL内部仍可减少的周期”。

raw是连续DRW流，利用MEM-AP自动增址回绕；**不是任意地址20KiB线性读写**。
实测这颗F103的回绕窗口为4096B，和DesignStart M0模型的1024B不同。
工具先用只读TAR观测检测窗口，备份完整窗口，再按实际偏移生成和校验数据；
不能跨窗口后仅检查返回长度就认定传输正确。旧 `dap_raw_benchmark.py` 没有这么做，
本轮不使用其数字。

另测127字=508B有效数据、512B读响应（需要ZLP），1000次、16深度：
50MHz读/写2.951/2.936 MB/s，60MHz3.011/2.917。小包更受固定开销和主机调用限制，
提高SWCLK不能按比例提高这组结果。此处为单轮补测，未算入上面三轮大包均值。

## 原版最新版 pyOCD

从PyPI在独立venv下载 **pyOCD 0.46.0**（本次查询最新版，2026-10-19发布），
没有修改其源码。依赖版本见 `measurements/pyocd046-environment.txt`。

使用通用cortex_m目标的真实SRAM API，CoreSight识别出Cortex-M3和AHB-AP；
MEM-AP自动探测窗口4096B。使用attach+halt，不reset；禁用memory/register/ELF缓存、
禁用auto_unlock，离开不resume，写入每轮flush，所有原SRAM均备份、恢复和校验。
4096B DAP packet和16个packet count均已确认。测试不包含初始化和关闭时间。

每个频率6个独立会话，每会话100次20KiB读和100次写：

| 原版API | 50MHz 读/写 MB/s | 60MHz 读/写 MB/s |
|---|---:|---:|
| read/write_memory_block32 | **1.692 / 3.037** | **1.846 / 3.056** |
| read/write_memory_block8，另3会话 | 1.342 / 2.478 | 1.392 / 2.484 |

60MHz限制仅1个在途packet的32-bit API，另3会话结果1.812/1.997。
这是原版pyOCD在本机的结果；不能用缓存读取或只计入队时间冒充探针吞吐。

已确认的实现差异：

- `cmsis_dap_core.py::transfer_configure()` 默认idle_cycles=2，raw/OpenOCD本机配置为1。
  idle=2下RTL仿真读/写上限仍有4.655/4.795 MB/s@60MHz，不能单靠这一项解释
  pyOCD读速降到约1.8MB/s。
- `MEM_AP._read_memory_block32()` 按4096B边界逐页调用 `_read_block32_page()`，
  后者同步等待 `read_ap_multiple()` 返回后，才进入下一页。
- PyUSB v2 backend 经独立接收线程、信号量和queue传递响应。
- 单独诊断的cProfile中，read_ap_multiple/get_result/flush/read_packet形成等待链；
  该轮的性能不计入上表。累计时间有嵌套，不能相加当成各环节占比。
- 设备分段计时中，pyOCD工作负载RTL块读/写均值661/644us，与此前651/631us接近，
  USB提交约3.18us；显著额外时间在设备执行之外。目标RCC前后完全相同。

结论是本机原版pyOCD没有提速，分页同步等待和线程/主机开销是有证据的方向，
但尚未逐项隔离贡献，也未在本轮改pyOCD来优化它。

## 与J-Link PRO的比较

SEGGER当前[产品页](https://www.segger.com/products/debug-probes/j-link/models/j-link-pro/)
标称最高4MB/s下载，接口最高50MHz。它是产品最高值，未必是这块F103上相同条件的结果，
且下载值主要对应写入，不能直接当读取也为4MB/s的证据。

以4.000MB/s为参照，本机raw写3.859相差约3.5%；OpenOCD写3.417相差约14.6%。
因此“底层离J-Link很远”和“应用层还落后”是不同判断。当前raw写已接近，线性API
仍有差距。若要稳过4MB/s@50MHz，读路径当前RTL上限只有3.956，必须减少RTL周期；
应优先解决idle=0可靠性、读路径额外状态周期，以及主机跨页流水。

本轮没有连接J-Link进行同板A/B，不宣称在真实性能上超过或追平其全部能力。

## 复现

```powershell
python tools/raw.py --speed 50000 --words 1022 --loops 1000 --depths 1,16 --output results/optimization/raw_repeat.json
python -m venv build/pyocd_latest
& build/pyocd_latest/Scripts/python.exe -m pip install pyocd==0.46.0 libusb-package pyusb
& build/pyocd_latest/Scripts/python.exe tools/benchmark_pyocd_sram.py --speed 60000 --sessions 3 --loops 100 --output results/optimization/pyocd_repeat.json
python tools/swd_throughput_budget.py
```

测试须独占DAP接口，不能与OpenOCD或另一测速进程并行。
完整数据、各会话数字和固件SHA256在 `measurements/20261026-raw-pyocd-budget.json`。

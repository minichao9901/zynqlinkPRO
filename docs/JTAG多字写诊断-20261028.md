# JTAG 多字 AP 写诊断（2026-10-28）

## 现象

板上，JTAG 传输、`DAP_TransferBlock`（0x06 … 0x0D）连续写 N 个字，再逐字读回：

| N | 正确 | 错误 |
| --- | --- | --- |
| 1 | 0 | — |
| 2 | 0,1 | — |
| 4 | 0,2 | 1（丢 bit0）、3（丢 bit0） |
| 6 | 0,1,2,4,5 | 3（残留上一次的值） |
| 7 | 0,1,2,4,5 | 3（残留）、6（bit1 错） |
| 8 | 0,1,2,4,5,6 | 3、7（都是残留值） |

规律：**第 3 个字开始出错，之后每隔 4 个重复一次**，错的值多为"上一轮同位置写过的值"或丢低位，
说明主机→目标方向的数据/地址在连续写时错位，而不是目标内存问题。

对照：

- 同一个 DAP 的 **读**路径是对的（8 个字全部读回正确，`read_pipe` 4.6 MB/s）；
- 单字写（N=1）永远正确；
- 把 TDO 采样相位钉成 0/1/0x10/0x11 都改变不了这个模式，说明不是接收采样相位问题，而是
  **AP 写的数据通路在连续写时丢/错位**。

## 影响

- `benchmark_probe_stream` / `benchmark_rtt_forward` 的 JTAG 路径要先把 4 KiB 测试图案写进目标
  RAM，因此全部失败（`06 00 01 04`、`06000104`）；
- `jtag_block_bench --transport jtag --write_pipe` 的数字**不可信**：它只数字节不校验，
  实际多字写是坏的。

## 下一步

在仿真里复现：用 `tb_jtag_pipeline` 的 JTAG 核 + DP 模型，连续写多个字并逐字比对，
定位是 `jtag_core` 的 DR 扫描拼接、还是 `dap_transfer_block_engine` 的地址推进/mux。
修好后重跑 `tools/board_jtag_write_probe.py`（正确后 16 个字应全部 landed），再补 JTAG 的 HSS/RTT 板级数据。

探针工具：`tools/board_jtag_write_probe.py`。

## 仿真复现（已修正：单笔传输路径是好的）

在 `tb_cm3_jtag` 里加了一段：CSW=0x50000032 → TAR=0x60004000 → 连续写 8 个字 →
直接读 `target.u_sys.mem` 比对。结果是 **8 个字全部正确**，AXI 上地址逐个 +4、strb 全 1111。

第一版"复现"是测试用例自己的错：把 CSW 经 `transfer(4, …)` 写到了 **DP CTRL/STAT**，
AP 的 CSW 一直是复位值（8 位、不自增），才会出现"地址不变、只有 byte0 有效"。
所以**单笔 DAP_Transfer 的多字写路径没有问题**。

## 真正的嫌疑：块传输（DAP_TransferBlock）

板上 `Memory.write` 走的是 CMSIS-DAP 的 **0x06 TransferBlock**（`[6, 0, count_lo, count_hi, 0x0D]`），
和上面验证的单笔路径不是同一条：前者进 `swd_controller` 的 block 引擎
（`dap_transfer_block_engine` / `swd_batch_engine`），后者是逐笔 `core` 请求。

所以下一步是把 **block 写** 放到 JTAG 下仿真：通过 0x30/0x38/0x3C 的 batch 寄存器写多个字，
再逐字比对目标内存；如果同样坏，就定位到 block 引擎在 JTAG PHY 下的地址/数据推进。

## 继续定位：batch 和 fast packet 均已覆盖，板级问题仍未修复

从 `45d7a5d` 继续的第一阶段没有保留生产 RTL 或固件修改，结果提交为 `02f6f39`。
以下结论替代上面的“下一步”假设；后续内部探测另见下节。

### 真实路径及仿真

`DAP_SWD_TransferBlock()` 对普通 AP 访问优先上传四字节压缩头，启动
`dap_transfer_block_engine`（0x40/0x44/0x48）；repeat batch 是回退路径，不能只测 batch。

`tb_cm3_jtag` 现在分别验证三条路径，并在数据不匹配时 `$fatal`：

1. 单笔 core 写 8 字；
2. batch：先 AP TAR=0x60005000；BATCH_ADDR=0，依次写入
   `0x0500080d`、8 个 payload、`0x0300000e`、END=0，再以 BATCH_CTRL=0x1003 启动；
3. fast packet：先 AP TAR=0x60006000；command BRAM 放 `0x0d000806` 和 8 字，
   PACKET_LEN=36、PACKET_CTRL=1。直接核对目标 SRAM，包含非零高位/低位图案。

三条路径均通过 CM3 真核仿真，含 WAIT 重试。增加 `bypass` 模拟 F103 的额外 IR5 TAP，
`target_clk_ns` 将目标 HCLK 与 PL FCLK 分开，`tdo_ns` 设置绝对返回延迟，
`writes_only` 可跳过与目标处理速度有关的 HSS 速率断言。默认目标时钟仍跟随 FCLK。

```powershell
python tools/run_cm3_sim.py --top tb_cm3_jtag --rebuild
python tools/run_cm3_sim.py --top tb_cm3_jtag clk_ns=10 target_clk_ns=13.888889 bypass writes_only
```

独立慢 HCLK 时，HSS 的固定 32-tick 周期可能无法凑满 124 点；这不是写测试失败，
因此这种配置使用 `writes_only`。修正 `axi3_sram` 中误写为字符串常量的 axitrace 开关，
避免默认打印每次 CPU 取指；runner 现在明确显示 Fatal 和三条写测试标记。

### 板级证据

实际加载 `prebuilt/20261028_swd_jtag/` 的 bit/ELF 配对；SHA-256、加载命令和结果保存在
`results/jtag/write_investigation_20261028/provenance.json`，不是根据当前目录猜测板上固件。
此配对本身仍有本问题，不能因称为基线就当作 JTAG 块写已验收。

增强 `board_jtag_write_probe.py`：测试前 halt，使用 SWD 单笔备份/恢复 SRAM；
JTAG 单笔写、块写分别写入图案，每轮先写反码防止残留值假通过，再以 JTAG 单笔读取比对。
`--batch` 可通过 XSCT 绕开固件，直接驱动 RTL batch。`--dump-command` 在读回前导出 command BRAM。
退出码 1 表示已经复现错误；JSON 的 `restore_match` 另行记录恢复结果。

```powershell
python tools/board_jtag_write_probe.py --speed 50000 --counts 4,8 --batch --dump-command --output build/jtag_write_probe.json
```

| 实际 FCLK / TCK | 检查 | 结果 |
| --- | --- | --- |
| 2 / 1 MHz | 2/4/8/16 字 | 单笔和块写均正确 |
| 50 / 25 MHz | 同上 | 均正确 |
| 66.67 / 33.33 MHz | 同上 | 单笔正确，4 字块写曾丢 bit23；短测其余通过不能代表稳定 |
| 100 / 50 MHz | 4/8 字，反码预填 | 单笔全部正确；packet 和直接 batch 都写坏 |
| 100 / 25 MHz | 保持 FCLK，仅 half-delay=1，mode=0 | 2/4/8/16 字均正确 |
| 120 / 60 MHz | 随机 2/8/64/256 字 | 前三组通过；256 字块写有 3 字仍为反码预填值，单笔全部正确 |

50 MHz 出错后 command BRAM 中的头和 payload **逐字正确**，包括 PIO 上传的 4 字和 DMA 上传的 8 字。
直接 batch 状态 `0x0000440a` 为完成、ACK OK、一个 RDBUFF 响应，目标数据却错；该引擎没有
`next_valid` 链接。因此不能再把问题仅归因于 USB 打包、DMA 上传或 packet 专属的 chaining。

还做过跨协议对照：JTAG 块写 8 字后，JTAG 单笔和 SWD 单笔读回完全相同的坏数据，
确认目标 SRAM 确实未被正确写入，不只是块读解析错误。连续写 AP TAR（request=5）也会错误，
不是 DRW 自增地址专属的问题。当前更应检查共用连续 AP 扫描的 ACK/接收窗口及引脚时序；
尚未证明某个具体 RTL 状态或物理边沿是根因。

### 已拒绝的实验

试过移除 `jtag_core.DR_NAV` 的两个前置填充位（TMS 偏移 4→2、TDI 偏移 5→3、总计数基数 7→5）。
新 bit 确实重新综合、布局布线、生成，配套 ELF 也重新编译（固件源码相同，ELF 哈希相同）。
120 MHz 时序 setup=+0.145 ns、hold=+0.053 ns；CM3 和协议模型仿真通过。
但上板校准下降到 TCK≈32.14 MHz，随机长包和单笔读回仍失败，恢复检查也失败。
**该实验没有修复问题，生产 RTL 已还原，失败 bit 没有替换 prebuilt 或标记为已验收。**

已重新加载原配对，并通过 SWD 从实验前的可靠备份恢复、核对 1024 字节 SRAM。
失败产物保留在 `build/jtag_exact_dr_candidate/`，文件哈希、失败结果和恢复记录见 evidence 目录。
“去掉填充位”不能作为当前修复方案；由于重布线也会改变物理路径，本实验也不能单独证明所有
填充/采样窗口问题均已排除。

## 第二阶段：无外接 LA 的片内被动扫描记录

用户确认没有连接 LA，并要求避免外部探头改变负载。新增 first-32-scan 记录，仅由独立诊断
CSR 显式武装；历史写满自动冻结，也可手动冻结。它不门控 PHY，不插入等待、不改请求和扫描长度。
`jtag_shift` 在每个 TCK 上升发出前记录内部 TDI 以及 IOBUF 的 pad 回读，在原接收时刻同时
保留选中/未选中 IDDR 相位。后者用来比较 ACK 窗口，不能单独替代目标引脚上的模拟建立保持测量。

每条 DR 记录保存前端数据、JTAG 核锁存数据、串行 TX 重建值、TDI pad 重建值、两种相位的 RX、
原始 ACK/CMSIS ACK、请求、phase、来源和时间戳。寄存器基址仍为 `0x40010000`：

| 偏移 | 含义 |
| --- | --- |
| 0xCC | 读：高 16 位签名 0x4A54，bit12 frozen，bit11 armed，bits10:5 count，bits4:0 head；写 3 清空并武装，写 4 冻结 |
| 0xD0 | 记录索引 0..31 |
| 0xD4 | 时间戳[31:19]，operation[18:16]，phase[15:14]，请求[13:6]，raw ACK[5:3]，CMSIS ACK[2:0] |
| 0xD8 / 0xDC | 前端写数据 / 核本次扫描锁存的写数据 |
| 0xE0 / 0xE4 | PHY 实际 TDI 位重建的 data / IOBUF pad 回读重建的 data |
| 0xE8 / 0xF0 | 选中 / 另一 IDDR 相位的 RX data |
| 0xEC | 来源标记、packet 状态、前端请求及两条 TX echo 的 RnW/A[3:2] |
| 0xF4 | [15:0] 选中相位扫描前 16 个采样，[31:16] 另一相位；保留导航位和邻近 ACK 窗口 |

`tools/jtag_internal_trace.py arm/dump` 通过 Zynq 自身调试口操作这些 CSR，不驱动目标的 JTAG。
`board_jtag_write_probe.py --internal-trace` 在地址配置完成后、块写发出前武装，块写回复后立即冻结/导出，
随后才读取目标 SRAM。CM3 用例对片内记录也做了实际数据一致性断言，不只检查签名。

```powershell
python tools/board_jtag_write_probe.py --speed 50000 --counts 4,8 --internal-trace --output build/jtag_scan_trace.json
```

诊断产物、时序和实板结果将在单独配对的 manifest 中记录。它用于定位现有 bug，不能仅凭 trace 功能
通过就宣称 JTAG 块写已修复。

### 内部 trace 已上板

`prebuilt/20261028_jtag_internal_trace/` 保存 RTL 源码提交 `6b14b58` 的诊断 bit/ELF 配对，
120 MHz 时序 setup=+0.145 ns、hold=+0.044 ns。该配对验收的是 trace 功能，块写 bug 仍在。
实板证据位于 `results/jtag/internal_trace_20261028/`，SRAM 恢复检查通过。

实际 FCLK≈100 MHz、TCK≈50 MHz、mode=17：4 字记录 10 次 DR 扫描，8 字记录 18 次；
所有前端数据、核锁存值、串行 TX 重建值和 pad 回读均一致，目标 SRAM 仍出现原有坏写。
后续每个字均先 WAIT 再 OK，Q1/Q2 返回的 ACK 位相同。最后 CTRL/STAT 为 0xF0000000，
没有 sticky error。这把重点移到连续扫描/未完成 AP 写的交互，而不是上游数据丢失。

### 可在同一 bit 内切换的 WAIT 提前退出实验

本地 CMSIS `JTAG_DP.c` 在 ACK 非 OK 时提前退出 SHIFT_DR；当前 RTL 则完成整个 DR 数据字段。
新增默认关闭的实验开关：CSR `0xF8` 高 16 位签名 0x5741，bit0=1 时，在收齐 raw WAIT ACK
后走 Exit1→Update→Idle，停止继续移入 32 位数据。仍按原有 WAIT 重试规则执行；未修改 OK 扫描。
不能仅从这一差异推定根因，要用同一个 bit 的开/关对照验证。

诊断 0xEC 的 bit31 现在标记该扫描已提前退出，bits30:24 记录实际 TCK 数；统计寄存器
0xC4 也改为累计实际扫描位数，避免把被截短的 WAIT 仍计成完整帧。工具对被截短的帧不要求
TX data 等于原本准备的整字，但依然比较 pad 与实际发送位。

```powershell
python tools/board_jtag_write_probe.py --speed 50000 --counts 4,8 --internal-trace --wait-abort 0 --output build/wait_exit_off.json
python tools/board_jtag_write_probe.py --speed 50000 --counts 4,8 --internal-trace --wait-abort 1 --output build/wait_exit_on.json
```

CM3 `abort_wait` 回归已覆盖实际提前退出（8 字测试中 7 次 WAIT 被截短），单笔/batch/packet
以及 HSS/RTT 均通过；RTT 为 65527 FCLK cycles，关闭时为 99322。该仿真性能变化不是板级测速结果。

# 4 MB/s @ 50 MHz 优化执行记录

## 冻结基线

开始提交：`3c01617`，分支 `codex/main-continuous-scheduler`。
固件配对：`f49bf49` 的 prebuilt bit/ELF；其SHA256仍见 prebuilt/SHA256SUMS。
测量明细：`measurements/20261026-raw-pyocd-budget.json`。
F103保持96MHz，无目标Flash编程；下列均为十进制MB/s。

| 50MHz SWCLK | 读 | 写 |
|---|---:|---:|
| RTL上限，idle=1，1022字 | 3.956 | 4.077 |
| raw，16条流水，3轮×1000包 | 3.796 | 3.859 |
| OpenOCD，20KiB，6会话×300轮 | 3.326 | 3.417 |
| pyOCD0.46.0，20KiB，6会话×100轮 | 1.692 | 3.037 |

## 验收目标和顺序

主目标：F103@96MHz、SWCLK50MHz，真实20KiB线性SRAM读/写均达到4MB/s。
至少10会话，完整数据、写完成和恢复校验。主机保持空闲，不能把缓存/入队速度当线速。
raw目标约4.15MB/s，为应用层留余量；512B响应另列，避免仅优化大包。
60MHz作为第二运行点回归，不靠提高SWCLK掩盖50MHz效率。

1. 重新复现idle=0失效，找出具体事务/边沿；先测试当前已修复RTL是否仍失败。
2. 缩短core完成到下一事务启动的间隙；命令/结果握手不允许越过ACK、奇偶校验或错误中止。
3. 在测量支持的前提下引入命令/响应双缓冲和轻量描述符队列，隐藏PS/CDMA/USB间隙。
4. 优化主机跨页流水；优先现有OpenOCD路径，pyOCD异步接口作为独立工作项。

每一有效节点commit；先mock/真实M0目标仿真，再上F103。保留保守回退和异常恢复。
不直接删除协议turnaround，不凭一次高值判定达标，不移除必要的写完成检查。

后续试验与实测追加在下方。


## idle=0：复现和高电平保持修复

解除固件的idle>=1钳位后，简单DPIDR/初始化可过；重复
DHCSR/RCC_CR/RCC_CFGR/SRAM的TAR写+单字AP块读时，idle=0在第10/14次
出现ACK=7（响应06000007），同序列idle=1连续100次通过。
这证明不能直接去掉钳位后宣布成功。

新增真实串行帧断言：写parity上升沿后、下一个SWCLK下降沿前，主机驱动的数据
不得改变。旧core在ST_DONE/ST_IDLE把swdio_o强制为1，旧RTL立即在1045001ps
触发该断言。修改为高电平保持最后驱动位，下一次请求在下降沿设置START；
从输入状态收回总线时使用低电平。修复后idle0/1/2串行预算仿真均通过。

packet mock/AXI错误与复位回归通过，真实M0目标1023字读写、WAIT恢复及执行中断
通过（idle0_parity_hold）。暂不宣称这就是全部F103失效原因；物理上板另验证。


工具节点：新增 tools/validate_idle_zero.py，只读比较idle1/0的短AP事务；
新增 tools/benchmark_cmsis_sram.py，使用标准CMSIS-DAP做真实20KiB线性内存API，
每4096B页显式TAR，不借助回绕重复数据；完整备份/恢复并检查RCC未变。
可用 --prefix-words 2 把TAR和两字数据放入0x05，剩余1022字走0x06，
每20KiB由15条命令减到10条；收益须在空闲主机上实测，不凭命令数量推断。
当前实现期间idle1控制样本数据与恢复检查通过，不作为最终速度验收。


上板：parity高电平保持修复后，50/60MHz各4组×1000次短AP访问通过（idle1/0交替）。
但是随机整块写后读仍出现ACK7；因此没有宣布idle0已可用。raw失败的自动恢复也曾
因DP失去帧同步而失败，之后用idle1、SWJ重连和已知原始20KiB备份恢复，整窗口SHA256
重新核对为df4d3d59729a5ed2a054e3014a2d54cb510211bdd53e1c04e3532e84b1ed14f9。
raw工具现在在恢复失败时先按保守idle1重连，再恢复，原测速仍保持失败。

追加RTL事务历史：0x54控制/清除，0x58读索引，0x5c读记录；保存最后16次实际
完成的SWD req/ACK/parity/序号，在非法ACK或parity错误时冻结。vendor0x88和
 tools/dap_transfer_history.py 可清除/读取，不依赖外接LA。当前正在实现这版诊断bit。

## 2026-10-27：第二处高电平违规

诊断bit在第13302次完成时冻结：前序AP读和RDBUFF全部ACK=1，下一次AP读
突然ACK=7；之前没有WAIT或parity错误。见实验输出
`results/optimization/idle0_failure_history.json`。不能将问题归咎于目标WAIT。

新增方向断言后，发现ST_DONE/ST_IDLE在SWCLK高电平收回SWDIO输出方向，
旧RTL在244255000ps触发断言。修改为读结束后保持输入方向，直到下一请求的
下降沿才收回；写parity的高电平数据保持也继续保留。方向修复通过idle0/1/2
串行预算、packet/AXI错误恢复以及DesignStart M0的packets/recovery/errors
回归（idle0_direction）。此节点尚待F103随机块上板验证，不宣称已彻底修好。

测试工具重连后显式DP ABORT清除sticky error，避免上次错误污染下一次实验；
线性SRAM工具也加入保守idle1重连的恢复兜底，原始测试失败仍然保留。
ACK hold诊断必须在Connect之后设置，因为Connect会重写整个CFG；真实hold=1
没有改善，不能作为解决方案。未修改目标Flash或运行时钟。

方向修复上板后，随机整块测试仍失败（初始写，ACK7），完整恢复4KiB校验通过；
历史显示TAR写后的RDBUFF先WAIT、再OK，之后AP写ACK7。
保守idle1对照500包：读3.773/写3.843MB/s，读写数据和恢复通过。
因此这两处修复不能当作零空闲已稳定的证据；prebuilt继续保留冻结基线。

## 连续完成握手与收尾状态合并

core增加next_valid/ready和result_valid，当前ACK=OK且无parity错误时才接下一笔；
packet引擎在busy保持高期间消费结果，写prefetch仅在真实成功时推进。
WAIT保留当前数据重试，FAULT/parity终止，不执行下一条；最后的RDBUFF仍保留，
错误/部分完成计数保持。其余batch/SWJ路径继续使用原start/busy接口。
RTL事务历史改由result_valid触发，连续busy期间也不会漏记。

读数据parity在最后采样前一拍归约，只给半周期输入路径留一个XOR。
读turnaround与parity收尾合并，写parity后直接进入idle；保持必需的turnaround、
配置的idle时钟及高电平数据/方向约束。仿真统计如下（1022字+最终AP drain）：

| idle | FCLK周期：读/写 | 50MHz RTL读/写上限 MB/s |
|---|---|---|
| 0（实验） | 95148 / 95150 | 4.296 / 4.296 |
| 1 | 97194 / 97196 | 4.206 / 4.206 |
| 2 | 99240 / 99242 | 4.119 / 4.119 |

不是硬件实测速率，不含USB/PS/DMA/WAIT。与冻结idle1读3.956/写4.077的上限相比，
读写不对称已在RTL周期预算中消除。串行断言、WAIT和中途FAULT/parity部分结果、
5组packet mock、AXI集成以及C传输队列回归通过；真实M0的idle0完整回归通过，
idle1/2扩展回归进行中。上板/性能验收尚未完成。

实现约束改为本分支实际使用的FCLK120MHz（SWCLK60MHz），不再强求180MHz布局。
仍使用分块OOC/IP缓存，仍检查routed setup及hold，安全频率有独立记录。

## 混合Transfer写命令压缩

普通0x05批量构建器把相邻同请求的写合并为现有repeat-write头和多个数据字，
遇到读或不同请求立即结束组；不跨越TAR/SELECT变更或posted-read drain。
保留最后的写完成RDBUFF。255条写由最多510字压成256字，减少DMA和RTL取头次数。

独立上板验证使用方向修复bit（不是尚在生成的chain bit）+新ELF：50/60MHz各
30轮、150个场景，覆盖7/8分派边界、255操作上限以及读写/TAR交叉；所有返回
数据和原始1KiB恢复通过。恢复SHA256与本轮最初20KiB备份的前1KiB完全一致。
真实串行batch仿真也通过1000字repeat-write+RDBUFF、WAIT/FAULT/parity和旧格式。
性能收益待同一新版bit上的对照测试，不能用压缩比推测速结果。

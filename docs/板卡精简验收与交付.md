# 板卡精简验收与交付

完整工作台验收采用七组清单，每组五项，按优先级排列，另做三轮跨页压力测试。定向修复执行受影响的板卡、链路和条目，并在报告中列出实际范围。上板、写入、固化和发布按本次授权执行。

## 板卡与固定档位

| 目标板 | SRAM、烧录、调试、RTT Viewer、RTT 转发、J-Scope | ETM |
|---|---|---|

除 ETM 专用的 SWD 10 MHz，每条链路只用表中一个档位。记录实际 FCLK、SWCLK/TCK 及其来源，注明是寄存器推算还是仪器测量。所选实际档位未达到时，记录实际值及原因，并把指定档位标为待验或失败。按下文对齐该档位的历史最佳有效成绩，每次接受新的板测结论都要对应实际配对和本轮证据。

开测前确认 ZynqLinkPRO J7 的 USB 序列号、当前 COM（如用）、bit/探针 PS ELF、目标固件和探针占用状态。保存本轮会改变的 Flash、SRAM、核心寄存器和外设配置。结束时独立核对恢复、目标运行或暂停状态及探针采集引擎状态。

### J-Scope 判定

- F103ZE 和 H743 分别做 SWD 单路、SWD 八路、JTAG 单路、JTAG 八路，共四个 60 秒确认窗口。HPM6800EVK 做 JTAG 单路和八路，共两个。各路使用相同宽度的已知数据，例如每路一个 u32。
- 固定链路档位，从已有稳定点附近短窗调整**采样周期**，只对单路和八路各取最快通过点做 60 秒确认。长窗失败时保留该证据，放宽周期后重新确认。
- 60 秒内探针跳拍率须严格低于 0.1%，USB 丢包、数据帧序号缺口、读错和 STOP 尾差均为 0。记录请求周期 ticks、实际收到的完整样本组数、实得组/s 和跳拍率。八路按一组八值计。分别保留测速窗和含 STOP 的会话最终计数。

## 跨页与断线压力测试

每块板在每条适用链路的固定档位各做 **3 轮**。在同一 Web 工作台会话中，每轮把 **RTT Viewer、RTT 转发、J-Scope、调试**各跑一次，顺序随机且三轮不同。启动后确认上行有连续序号、采样有已知值或调试已经暂停并可读 PC，再执行该次切换或断开。采样和收数使用短窗。

每轮给四项业务各分配一种结束方式，跨轮轮换对应关系，让同一种断开落到不同业务上。安排第 3、4 种在三轮中分别覆盖 RTT 收数中、J-Scope 采样中和调试暂停。

1. 正常停止或退出当前业务，直接切到另一页启动业务。
2. 正常停止或退出后，在空闲态点断开，再连接。
3. 工作中点断开，再连接。
4. 工作中断开 J7 的 USB 数据连接，再接回。已确认可操作且能保持探针与目标供电时执行，否则将物理断线项记为待验。串口重新枚举后按 J7 序列号核对实际 COM。

每次重连后，先验证断开前的业务可重新启动并收到新数据或完成一次暂停/单步，正常退出后再继续轮换。正常停流核对序号连续，RTT 转发和 J-Scope 另核对 STOP 尾量。故意断线时保留中断状态和可验证的数据边界，重连后的新会话须无旧包、无卡死、无上一业务占用残留且数据继续前进。调试断开后核对目标实际运行或暂停状态，清除本轮临时断点。三轮结束后核对目标恢复、探针空闲及下一次连接可用。

记录每轮实际顺序、各业务对应的结束方式、重连耗时、异常和恢复结果。若使用脚本打乱顺序，同时保存随机种子。首次异常保留步骤和日志，刷新、重启或重载后的结果单列。

## 一键执行

在仓库根目录预览计划。可用 `--transport` 和可重复的 `--only` 选范围，`--seed` 复现随机顺序。

```powershell
python -X utf8 toolbox.py project run board.accept -- --board f103ze
```

为本轮启动独立的本机源码工作台。下例使用 J7 的正式 QSPI 配对，临时加载配对时同步替换两个路径。打开服务输出的鉴权地址并保留一个工作台标签页。

```powershell
python -X utf8 toolbox.py --runtime build/accept-web-f103 serve --native-probe --bit prebuilt/qspi-release/probe.bit --zynq-elf prebuilt/qspi-release/application.elf
```

另开终端执行。以下示例针对已确认运行 CDC48、原 SWJ_CFG 为 2 的 F103ZE，授权擦写并复位目标时才加 `--allow-flash`。

```powershell
python -X utf8 toolbox.py project run board.accept -- --board f103ze --runtime build/accept-web-f103 --out build/accept-f103-new --f103-restore-swj 2 --allow-flash --execute
```

- 每条用例和每一压力轮都即时输出 JSON 行。目录中有增量 `events.jsonl`、总表 `summary.json`、各项原始证据和私有恢复备份。可恢复的失败继续后续项目。恢复或写入结果未确认时剩余项记为阻塞，并输出总表。退出码 `0` 表示所选范围通过，`1` 表示有失败或阻塞，`2` 表示仍有待验。全范围通过才设置 `accepted=true`。
- 默认匹配 J7 序列号 `12345678`，COM 按序列号动态发现。XSCT 有多个候选时可用 `--jtag-cable-serial` 指定 J7 下载线。预检在探针空闲时改变并恢复 JTAG 采样模式，由 AP0 同步读回绑定同一物理探针。配对证据记录 OCM 执行代码、实际 PL 能力寄存器与声明文件的 SHA-256。现有正式 RAM/QSPI 配对使用同一已收录 PL 配置，其他 bit 需先有对应的实板识别证据。寄存器识别的范围是 PL 配置特征。现有原生 ETM 仍要求只有一只同 VID/PID 的探针在线。
- 烧录使用与板上相符的 `--target-elf`，备份涉及的扇区及算法工作区，并对照真实 Web 和原生 OpenOCD。HPM 原生烧录需传对应 SDK 的 `--openocd` 与 `--openocd-scripts`。本入口重新烧录原应用，独立读回并恢复工作区后确认复位及心跳。F103ZE 用接到目标的 J7 NRST，核对拉低、释放、DHCSR 新复位标志和启动后的连续心跳。F103ZE 的 JTAG 夹具临时打开 AFIO 后，原生 OpenOCD 和 Web 连接分别在扫描前选择 ARM JTAG，测量仍用 60 MHz 档。擦写中断后先确认写入端退出，再读回或回滚。Flash 恢复未确认时禁止自动恢复运行，保留备份和日志。
- 调试及相关压力用例从运行中的原应用开始。结束时恢复本轮涉及的断点配置和运行状态，应用从实际执行到的位置继续，保留栈、寄存器和 RAM 的自然进展。已暂停的应用在这些用例中记为待验。H743 的 ETM 使用 CPU60/TRACE20 基线执行 `--only etm` 补测。
- ARM/JTAG 的 RTT 转发和 J-Scope 可以运行原生对照。当前 Web 只提供 ARM/SWD 和 RISC-V/JTAG 流模式，ARM/JTAG 网页和相应跨页动作为待验。J-Scope 的 60 秒窗口报告最快通过的已试周期，并保留短窗与长窗失败点。
- 物理断线默认记为待验。能保持探针和目标供电时，交互终端可加 `--usb-data-cycle`，按提示拔插 J7 数据线，程序确认消失和重新枚举后继续。

各板分开执行，换板后使用新的证据目录。最后给出全部结果目录，包括 H743 单独的 ETM 补测目录，离线汇总判定。汇总要求相同的源码提交和探针对，并按板绑定实际核验过的目标 ELF，ETM 单独绑定采集用 ELF。只有通过项且具备对应 ELF 证据才可纳入通过结论。按用例选择最新结果，原报告保留首次失败和重跑记录。

```powershell
python -X utf8 toolbox.py project run board.accept -- --review build/accept-f103-new build/accept-h743-new build/accept-h743-etm build/accept-hpm-new --out build/acceptance-review
```

## 验收后的收尾清单

在本轮报告中勾选每项。未完成的写明「待办」和原因，超出本轮交付范围的标记「不适用」。有失败、待验或阻塞时也执行收尾并保存已有证据。

### 每次验收必做

- [ ] **核对最终结果。** 保存每项、每轮和最终汇总。核对计划与实际完成项，记录通过、失败、待验、不适用和阻塞，以及实际档位、性能和三轮压力结果。性能记录逐项附历史最佳证据、对齐条件与差值。首次失败与后续复测都保留。
- [ ] **恢复并复核现场。** 按本轮涉及范围核对 Flash、RAM、核心寄存器、临时断点、外设配置和时钟。记录最终运行或暂停状态，确认 RTT/HSS/ETM、DDR/DMA 空闲，以及本轮 USB/HID/COM 已释放。未操作硬件时记不适用，恢复未确认时保留现场和备份。
- [ ] **归档可复核证据。** 在 `docs/validation/` 更新本轮报告和证据索引，记录源码提交、工作台入口及版本/构建时间、板卡、探针序列号、配对和目标 ELF 哈希、实际时钟及其来源。需要保留的 Trace 记录配上所用 ELF 和原始证据。大文件和私有备份注明存放位置，检查交接链接。
- [ ] **检查并同步问题表。** 登记新问题，更新复现变化、修复、失败及能力边界，沿用已有编号。按本轮证据写明关闭范围和仍待补验的项目。[项目问题跟踪列表](项目问题跟踪列表.md)

### 按交付范围触发

- [ ] **命令、路径或流程有变化。** 更新受影响的 README、CLI 指南、可执行 Web 手册和发布说明。从实际入口复核操作、参数和路径。手册有可执行步骤变更时，用本机手册验证受影响步骤。
- [ ] **交付 RTL、Zynq 固件或目标夹具。** RTL、Zynq 固件或相关构建配置改变时，提交实际验收用的 bit/PS ELF 和 manifest，记录源码提交、构建参数、时序、SHA-256 和实板范围。目标夹具改变时同步源码、配套目标 ELF 及验收证据。分开记录临时加载和 QSPI 冷启动。
- [ ] **交付新的 QSPI 固化镜像。** 完成写入、BOOT 读回、实体冷启动和 OCM 核对后，将 BOOT、配套 bit/PS ELF、辅助文件、清单和验收出处更新到 `prebuilt/qspi-release/`。保留可回退版本。仅换镜像时，Web 和 CLI 沿用固定路径，若交付含推送，则随 `main` 同步。[正式 QSPI 目录](../prebuilt/qspi-release/README.md)
- [ ] **复核公开 QSPI 交付。** 推送后匿名打开现有 Pages 的 QSPI 下载入口，确认它指向远端 `main` 的 `prebuilt/qspi-release/`，记录远端提交。下载该提交的 `flash_manifest.json`、BOOT、配套 bit/PS ELF 及清单列出的文件，核对公开文件 SHA-256 和本轮签收的清单。仅换镜像同样执行此项。[发布流程](github-release.md)
- [ ] **交付本机工作台。** 先验收冻结候选，再更新固定 `dist/zynq-etm-bridge/`，保留 `data/` 并归档旧程序。实际从固定 EXE 启动，复核版本、构建时间和受影响功能。
- [ ] **提交或推送 Git。** 按任务范围提交本轮源码、文档、证据和适用的正式产物。任务要求推送时，推送到 GitHub `main`，读回远端分支并确认已包含交接提交。仅补源码、验收工具、文档或证据时，按本轮范围完成提交或推送即可。
- [ ] **正式对外发版。** 从同一已提交源码构建 Pages 和 Windows ZIP，更新 GitHub `main`、`gh-pages` 与 Releases，上传 ZIP、SHA-256 和发布说明。仅换 QSPI 镜像时沿用现有 Pages 和 Windows 包。[发布流程](github-release.md)
- [ ] **复核公开交付。** 匿名打开公开 Pages，核对版本、构建时间、下载入口与 Release 标签。完整下载正式 ZIP 并比对 SHA-256。若交付范围包含线上实板验收，从公开 URL 复测并保存结果。提交发布证据，再确认远端 `main` 包含此提交。[发布流程](github-release.md)

### 每次收尾必查

- [ ] **结束本轮进程。** 关闭本轮启动的浏览器会话、服务和子进程。保留共享 `hw_server`、其他会话及另一只探针的连接。
- [ ] **先归档，再清临时文件。** 保留报告引用的证据、首次失败记录、匹配 ELF、私有 Flash/RAM 备份和可回退包。按明确目录清理本轮临时浏览器配置、令牌、重复下载、解包和弃用候选。检查共享 `build/`、固定安装、用户 `data/` 和采集记录仍可用。
- [ ] **清理 Git 临时工作。** 检查本轮分支和 worktree。已合并的临时工作在核对交付提交和所需远端同步后清理。明确弃用的方案在核对改动归属后清理。保留他人的改动和仍需复测的候选，最后检查工作区和本轮后台进程。
- [ ] **给出交接。** 写明提交号、验证范围、问题编号、未完成项和现场恢复结果。远端 `main`、本机固定 EXE、公开 Pages、Release 下载包、J7 实际冷启动镜像各填一项，附各自的提交、版本/构建时间、SHA-256 或现场证据。

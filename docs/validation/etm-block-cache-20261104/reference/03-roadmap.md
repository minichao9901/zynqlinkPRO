# 03 · 实施路线

> 假设：1–2 人全职，C++ 熟手，有 Cortex-M 调试经验，手上有 J-Trace Pro + 一块 M7 板子。
> 单人 ~30 周，双人 ~18 周。

---

## 1. 里程碑

| 阶段 | 目标 | 交付物 | 验收标准 | 工期(单人) |
|---|---|---|---|---|
| **M0** | 骨架 + CI | `etraced` 库、CMake、6 个自测 | `ctest` 全绿；1M 条穿过流水 <50 ms | 1 周 ✅ 已完成 |
| **M1** | 展开层 | `flow.hpp` + `thumb.hpp` 完整版：IT 块、异常、调用帧、基本块缓存 | 合成代码 100% 正确；吞吐 >200 M inst/s | 4 周 |
| **M2** | ETMv4 包层 | `etmv4.cpp`：64 项分派表、变长载荷、地址压缩、同步/失步、时间戳 | 规范附录样例全过；与 OpenCSD 对拍 0 差异 | 7 周 |
| **M3** | 数据接入 | `ITraceSource` 三实现：J-Link RAWTRACE / 文件回放 / 自有探针 | 真板子连续抓 10 s 不丢不崩 | 3 周 |
| **M4** | 模型层 | `TraceStore` 完整版：块、调用帧索引、覆盖率、导出 CSV | 10 M 条内存 <200 MB；UI 查询 <10 ms | 3 周 |
| **M5** | UI | Qt6 Model/View：指令窗口、时间轴、代码覆盖热图、源码联动 | 60 fps 滚动 10 M 条；启动 <2 s | 7 周 |
| **M6** | 硬化 | 长稳测试、错误注入、打包、文档 | 连续 8 h 无泄漏；丢包场景 UI 正确告警 | 4 周 |

**关键路径：M2 → M3**。M2 卡住整个项目，所以：

> ⚠️ **M2 必须并行准备对拍环境**。在写解码器之前，先把
> `raw.bin + OpenCSD 输出` 的流水线跑通。否则你会在"看起来对"和"实际错"之间反复横跳。

| 周 | 可见成果 |

| 23–26 | 性能达标、长稳、打包 |

## 3. 技术选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **C++20 + Qt6** | 与 Ozone 同构；性能最好；Qt Model/View 天然适合百万行虚拟列表 | 构建链重；license（LGPL 可商用） | ✅ **推荐** |
| Rust + egui | 内存安全；单二进制 | 生态弱；虚拟列表要自己写；招人难 | 备选 |
| Electron + Web | UI 快 | 解码性能不够，必须写 native addon，等于两套 | ❌ |
| Python + Qt | 原型快 | 解码慢 100×，只适合做对拍脚本 | 只用于测试工具 |

依赖库：

| 用途 | 选型 | 备注 |
|---|---|---|
| 反汇编 | Capstone 5 | 只用来**显示**，展开层用自己的轻量解码（快 10×） |
| ELF/DWARF | libelf + libdwarf，或 `elfio` + `libdwarf` | 行号表可能很大，要懒加载 |
| 参考解码器 | **OpenCSD**（BSD-3） | 只用于对拍，不链进产品 |
| 测试 | Catch2 / GoogleTest | |
| 构建 | CMake + Ninja + vcpkg | |

## 4. 风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| ETMv4 细节理解错（尤其投机/IT） | **高** | 高 | 对拍 OpenCSD；先做 ETMv3（简单）再上 v4 |
| 没有真实抓包数据 | 中 | 高 | 第一时间买板子 + J-Trace；用 SEGGER 输出做第二参考 |
| 性能不达标（<100 MB/s） | 中 | 中 | 基本块缓存 + 页缓存，M1 就把这条压测做掉 |
| UI 卡顿（百万行） | 中 | 中 | 虚拟列表 + 增量 diff，绝不整表重建 |
| J-Link SDK 许可限制分发 | 中 | 高 | 产品化阶段切自有探针；SDK 只用于内部对拍 |
| 反汇编显示与执行不一致 | 低 | 中 | 展开与显示共用同一份指令长度判定 |
| 多核 / 安全态扩展 | 低 | 低 | 接口预留 `context_id` 字段 |

## 5. 硬件清单（预算 ~¥3000）

| 件 | 型号 | 用途 |
|---|---|---|
| 目标板 | STM32H743 Nucleo / H750 | ETMv4，480 MHz，带 trace 口 |
| 探针 | J-Trace Pro Cortex-M | 已有 |
| 转接 | 19-pin Samtec FTSH 转接板 | 飞线到 Nucleo |
| 逻辑分析仪 | 可选，抓 trace 引脚验证物理层 | |

> 先用 STM32H7 的原因是它 ETMv4 + 480 MHz，能把性能和正确性一起压出来。
> M3/M4（ETMv3）留作回归，因为老芯片的包更简单，便于定位问题。

## 6. 验收基准（写进 CI）

| 指标 | 目标 |
|---|---|
| 展开吞吐 | ≥ 300 M inst/s（单核，基本块命中） |
| 端到端延迟 | 从探针收到字节到 UI 可见 < 150 ms |
| 内存 | 10 M 条 trace < 200 MB |
| 正确性 | 与 OpenCSD 对拍，地址序列 100% 一致 |
| 丢包容忍 | 探针溢出后 500 ms 内自动恢复同步 |
| 长稳 | 8 h 连续抓包，内存增长 < 5% |
| UI | 10 M 条滚动 60 fps |

## 7. 差异化（不然只是"又一个 Ozone"）

1. **开源解码库**：把 L0–L3 做成独立 MIT/BSD 库，别人可以拿去嵌到自己工具里。
   生态一旦起来，护城河比 UI 深。
2. **跨探针**：支持 J-Link、CMSIS-DAP（部分）、自研探针。用户不被硬件绑死。
3. **离线优先**：trace 文件格式开放 + CLI，方便 CI/回归/分享。
4. **脚本化**：Python 绑定，让用户能写"自动找热点函数"的脚本。
5. **多核/多上下文**：Cortex-M55 + Ethos-U 这类异构平台是空白市场。

## 8. 现在就能开始的三件事

1. 跑 `etraced/build/selftest.exe`，读懂 `flow.hpp` 的状态机。
2. 按 `02-decoder.md` §4.2 把 `thumb.hpp` 补全到全指令集（一周）。
3. 用 J-Link 的 `JLINK_RAWTRACE_Read` 抓 1 MB 真数据，先把"统计信息"打出来
   （包类型分布、平均包长），这一步不需要正确解码也能做，但能极大加速 M2。

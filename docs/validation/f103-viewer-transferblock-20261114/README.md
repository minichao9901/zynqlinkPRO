# F103ZE JTAG RTT Viewer 块传输实板对照

2026-11-14，ZL-238。基线为 `3e29af39` 的 Viewer，候选使用本机工作区。只用 zynqlinkPRO J7 USB `12345678`、下载线 `210299008529`。物理 MEM-AP0 核对 `prebuilt/qspi-release/` 的运行 OCM 85,716 字节和 PL 特征。探针 bit SHA-256 `dd69106c46a4bd1a52badecbf9125e51beca8435c25d2742cca62323efaaf4e6`，PS ELF SHA-256 `64d00fe597030175920b994e39ff51db8a683dbb8d5f907c0f8d73f8d55044b9`。目标 STM32F103ZE 的 CPUID 为 `0x411fc231`，DBGMCU ID 为 `0x10036414`，CDC48 的两个 Flash 加载段共 20,168 字节与 ELF 一致。未写 Flash 或 QSPI。

## 条件与判据

- 浏览器为同一台 Windows 主机上的 Chrome。代理通路使用 `toolbox serve --native-probe` 的本机 USB 服务；直连使用真实 `USBDevice` 和 J7 的既有授权，页面资源从本机加载。Chrome 直连轮次逐一核对序列号，并统计实际 WebUSB 端点命令。
- CDC48 的 CPU/HCLK 48 MHz，CPU TAP `0x3ba00477`、边界 TAP `0x06414041`，MEM-AP0。每轮用同一 `probe_rtt_ram.S` 在 RAM 连续发布 u32，控制块 `0x20000200`、8 KiB 阻塞上行环 `0x20001000`、64 B 下行环 `0x20004000`。终端模式与 5 ms 轮询相同，记录自动渲染抑制的实际状态。实际 FCLK 119,999,998 Hz、TCK 59,999,999 Hz，由物理 PLL/分频寄存器读回计算。候选的数据阶段 idle、TDO 相位和基线有差异，分别报告。
- 首字节收到且物理时钟核对后，连续计 3 个约 3 秒窗口，列逐窗实收和中位数。整轮从序号 0 校验到最后一个完整 u32，单独保存跨环和 60 秒运行证据。下行写 `00 a5 ff 31 32 0a 80 55`，退出浏览器会话后用独立 SWD 回读全环，要求 WrOff 从 60 到 4、RdOff 保持 60、环内其余 56 个保护字节均为 `0x6e`。

## 修复与实测证据

Wasm 负责识别已打开的 JTAG 链、目标与初始 RTT 控制块。仅在 J7 确认 F103ZE 的双 TAP、AP0、芯片身份和 SRAM 范围后，由新的独占 USB 租约接管。上行 `DAP_TransferBlock` 按 1 KiB TAR 边界切分。下行用 `DAP_Transfer` 和边缘字节 lane，避免改写相邻字节。重新扫描时将链路交回 Wasm。

修复前两种通路全程只见 `0x14` 扫描，分别 2,914、7,533 条。候选初测桥接 128.27 kB/s、直连 869.89 kB/s，已证实块传输可减少同步扫描往返。复测在 60 MHz 看见 `06 01 00 03` 和 `05 01 03`，涉及块读/写和普通游标写，失败轮保留。切换普通写后仍需处理高频 ACK，调高 idle 本身不足以消除。模式 16 和 17 均通过独立原生 5 秒探测，各完成约 1,340 次上行读与游标提交，模式 0/1 首批失败。候选在 60 MHz 用模式 16 重新确认 TAP，预留 idle 15。

仅对已收齐的 ACK 3 回包复位 TAP、重新识别 CPU TAP 和清除调试端口状态，块读可重试一次。游标写先读回，确认仍是原值时补交一次。下行载荷只读回确认，短响应、超时和未知游标值会停止当前会话。独立的 JTAG 相位诊断第一次收尾误用了未启动的浏览器检查，随后已用私有备份完成 RAM、核心寄存器、FPB、AFIO/APB2 回写、读回及运行状态核对，之后复测时每轮正常恢复。

|---|---|

## 实现

三个独立研究开关，默认均0：

| 开关 | 作用 |
|---|---|
| `ETM_EXPERIMENT_ETMV3_PAGE_CACHE=1` | `OcsdCodeFollower`中按128KiB地址页、半字槽直接索引；首次成功调用原CPU解码器，存size、opcode、type/subtype、next ISA、conditional/link及静态next。 |
| `ETM_EXPERIMENT_STREAM_DENSE_SITES=1` | 增量统计的单指令范围直接索引到原Plan，命中仍检查end，避免每次unordered_map查找。 |
| `ETM_EXPERIMENT_STREAM_GROUP_PLANS=1` | 对同一待提交序列保存组合Plan，一次更新频次，再按源位置/调用帧批量统计。哈希命中后逐项比较完整Plan指针序列，碰撞不会被当作相同代码。 |

指令缓存实测 **20B/槽**，不是复制材料的32B私有结构。最终F103原始输入命中 **19,565,167**、未命中 **642**，首次解析量与唯一PC数对应；上一轮完整状态memcmp缓存约98%命中，本轮避免比较/复制非指令固有状态并预存后继。

缓存仅在不可变代码镜像、Cortex-M/Thumb且关闭解码器IT跟踪的受限路径启用，其他模式走原逻辑。架构/profile、内存访问规则、CSID和接口改变时失效；DSB/DMB选项改变也失效。N仍取顺序地址；E的直接分支用静态目标，E的间接分支继续等待Trace地址；错误/NACC不缓存。没有从Trace学习指令语义，未修改Thumb分类器。

新统计路径最终用编译期分流：ETMv3使用可选优化实例，H743/ETMv4及紧凑参考使用原实例，避免让它们经过新增的运行时缓存/组合分支。早期跨协议版本和仅运行时限制版本的失败都保留。所有场景仍处理完整输入，没有省略未成立/未知执行、包诊断、调用边或累计火焰图。

**边界：** 固定镜像是前提，未实现动态代码/目标实时内存失效协议。按需分配页在本次F103仅覆盖很少代码页；尚未做面向任意稀疏地址空间的统一缓存内存预算。只有这里的固定样本/模式已验收，不能直接默认推广到任意CoreSight消费者。

## 20MHz与J-Trace 150MHz不能直接按倍数比较

SEGGER公开规格分别列出最大TRACECLK150MHz、TPIU300MHz，并使用USB3.0 SuperSpeed：[规格](https://www.segger.com/products/debug-probes/j-trace/)、[USB建议](https://kb.segger.com/J-Trace_USB_recommendations)。按4位DDR计算，引脚理论线速为 `TRACECLK × 2 × 4 / 8`：20MHz约20MB/s、150MHz约150MB/s，包含线上的封装/同步/填充，并非同等数量的有效ETM载荷或恢复指令。

保存的H74320MHz/1秒记录只有2,176,688B解复用ETM，却恢复18,373,686条指令记录。这说明当前主机处理面对的是约2.18MB/s压缩输入及1837万条/s逻辑展开，不是在软件中逐个处理20MHz引脚边沿。将同一程序的端口时钟提高而CPU/执行路径不变，通常提高的是出口容量/减少端口拥堵，不能简单把主机解码工作乘7.5；具体仍受配置和同步/时间包影响。

高速接收逻辑负责引脚采样/打包，主机按块接收，USB3的带宽层级使150MB/s线速的传输在工程上可实现；这不证明它能对任意CPU/负载满速完成所有在线分析。SEGGER也明确记录“探针发来数据快于主机分析，丢弃并停止流式”的情况：[溢出说明](https://kb.segger.com/J-Trace_overflow_error)。采样/传输规格、在线解码吞吐、统计/历史索引/GUI是独立预算。

本仓库当前F103样本每秒约1957万次单指令范围回调，再进入元信息、归约和调用路径。商业实现可能减少中间表示并直接累计缓存项；公开资料不足以确认它的全部私有算法。我们的局部缓存收益是实测事实，不能用最高接口频率推导双方的解码速度，也不能据此否认我们当前软件热路径仍有差距。

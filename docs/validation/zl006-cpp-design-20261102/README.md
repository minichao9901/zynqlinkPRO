# ZL-006：C++ 全流程重构评估

日期：2026-11-02（Asia/Shanghai）。源码基线 `22b0352`。本轮是历史计时复核、当前源码审查及架构建议；没有实施性能优化、重跑性能基准或操作硬件。以下目标均未验收。

## 结论

建议将主机 ETM 数据处理收敛为一个 C++ 核心：前端解帧、OpenCSD、执行流/调用栈、存储、索引、查询和导出共用实现；Python 保留硬件事务与 Web 服务调度，JS 保留交互和绘制。优先融合现有 C++ 模块，移除大中间文件和重复扫描，再迁移剩余热点；不从零重写 ETMv3/ETMv4 协议解码器。

当前主链已经是 C++ OpenCSD + C++ builder + Python/NumPy 索引及发布，没有逐指令 JSONL，也没有逐指令跨 Python 调用。不能把混合语言直接认定为根因。NumPy 本身大量使用原生运算，逐句翻译成 C++ 不保证提速。

## 已有测量与本轮复核

数据来自 [11月1日审计](../zl006-decode-audit-20261101/README.md) 及其 `raw/current/trial-{1,2,3}/decode-performance.json`，本轮重新计算中位数：

| F103 固定大输入阶段 | 秒 |
|---|---:|
| 完整离线 API 处理 | 22.031 |
| OpenCSD 子进程（含输出 native.bin） | 1.888 |
| Store/索引整体 | 17.976 |
| 其中 C++ nativeBuild | 6.356 |
| 其中 queryIndex | 4.711 |
| 其中 assemble | 2.351 |
| 其中 inputBindings | 1.229 |
| queryIndex 内默认视图生成 | 2.973 |

上述分项包含嵌套，中位数也不一定来自同一轮，不能逐行相加。`decode_stream._run_native()` 的 OpenCSD 计时覆盖子进程启动、解码、回调序列化和文件输出，并非纯协议 CPU 时间。应补充纯 sink 对照才能判定协议解码上限。

F103 输入为 5,892,279 字节、19,565,799 条路径指令记录，native.bin 为 1,305,247,716 字节，约为原始 ETM 的 **221.5 倍**。`trial-2/decoded.json` 保存了 19,573,933 个 element 与 4,784,167 个 packet；`decoder.cpp::BinaryWriter` 对每个 element 固定写 61 字节、packet 写 22 字节头加原始包。仅 element 固定记录就约 **1.194 GB**。该样本 ranges 与 instructions 相等，范围记录没有带来多指令摊薄收益。这是当前 F103 表示膨胀的直接证据，不能据此泛化所有 ETMv3 配置。

H743 必须另列：[最新综合报告](../h743-comprehensive-20261101/README.md) 中约1836万条、0.325GB native，解码/建库中位10.303秒，完整CLI中位14.030秒，不含浏览器首屏。F103 的约32.6秒 Web E2E 来自另一组板测。不能混合输入、协议、缓存和计时边界比较。

## 源码对应与优先顺序

1. `etm-service/native/decoder.cpp`：OpenCSD 回调先写 element/packet 到 native.bin。将回调输出改为 C++ 内部事件 sink，直接送入 builder；旧 BinaryWriter 保留为诊断适配器。包计数、错误、偏移和完整性检查仍在在线处理时执行，原始 ETM 保留供包详情重放。
2. `etm-service/tools/native_pipeline.py::write`：先 hash native，再 prescan、静态字典、native build、facts 读回、索引、整库组装及输入绑定。将这些职责逐步移入同一核心，避免先写大文件再多遍读取。静态指令字典按 ELF 身份与地址/ISA 缓存，初期可保留现有唯一范围准备；后续采用可增量插入字典，不能盲目线性反汇编 ELF 中的数据区。
3. `etm-service/native/storebuild.cpp`：已经有执行状态、调用栈、路径段、facts 及部分索引事实。抽取可复用类，直接累计 cell/热点/调用树/导航数据；避免为下游再构造全量逐指令数组。范围和重复段压缩必须保留条件执行、异常、周期及边界语义。
4. `etm-service/tools/native_facts_index.py::build_full_index`：默认 window/timeline 约占索引阶段63%，应先分析这部分查询遍历和物化，再评估剩余 NumPy 运算迁移。建立 C++ 查询接口，同时复用现有语义作为差分参考。
5. 发布阶段采用分块写入、块校验、最终目录/manifest 原子发布，减少完整 store 的搬运与重组。hash 融合读写时计算，但必须先保证输入快照不可变；不能简单缓存旧 hash 或只看文件时间来删除输入变化检测。旧文件格式兼容和新格式版本需要显式管理。

优先级为：**消除 native.bin 必经落盘 → builder 与索引融合 → 默认视图/发布 → 剩余热点 → 协议层专项优化**。这是基于现有证据的工程判断，尚无各项实际收益。

## 建议模块与接入边界

```text
保存的 formatter / ETM 数据，或未来流式输入
                    ↓
  libetm_core：解帧 → OpenCSD → 执行流/调用栈
                    ↓
       分块存储 + 增量索引 + 质量/身份绑定
                    ↓
       查询 / 默认视图 / 区间明细 / 导出
                    ↓
  Python 服务适配 → HTTP/WebSocket → JS 页面
```

所有箭头上层传任务、路径、配置、分页结果或有界批次，不传数千万个 Python/JS 指令对象。建议先给核心提供一个 `etm_engine` CLI/worker，复用现有 Python 服务和冻结 EXE 打包方式；查询需频繁调用时使用常驻 worker，避免每个鼠标动作启动进程。核心与进程入口分离，未来需要 DLL 时再提供稳定 C ABI；Python ctypes/pybind11 或 Node N-API 都只是适配选项，不必同时维护两套。

初期硬件 USB 控制继续由现有单一所有者管理，C++ 接收保存文件或字节块。真正连续采集另立阶段处理 DDR/DMA/USB 所有权、背压和丢数检测，不能为了软件重构同时改写已验证的硬件恢复逻辑。

首屏、完整处理与持久化完成分别报告。可先发布明确标注覆盖区间的预览，但预览不能冒充完整处理完成；精确区间明细保留全部记录，视图缩放的分辨率适配不能改变全量统计。

## 对标 J-Trace Pro / Ozone 的含义

[SEGGER 官方 streaming trace 说明](https://www.segger.com/products/debug-probes/j-trace/technology/streaming-trace/) 描述了连续回传与目标运行时实时分析、profiling 和 coverage。它没有给出与本项目相同输入的可复现解码秒数，也没有公开足以复刻的内部数据结构。本文架构是工程建议，不是对 Ozone 内部实现的断言。

应分别对标：停止后可查看延迟、区间导航/缩放延迟、持续吞吐、峰值内存、完整性和调用/周期语义。真实持续分析要求每秒处理能力超过每秒输入，并有余量；当前F103样本约5.89MB ETM/秒、1957万路径记录/秒。1秒窗口花5秒处理即使体验大幅改善，仍不叫实时。原生解码子进程1.888秒含巨量输出，因此既不能据此保证实时，也不能据此断言纯OpenCSD一定达不到实时。

单条 trace 的地址、上下文、IT状态、返回栈等具有前后依赖，不能任意切字节并行解码。先顺序解码状态，再并行独立块的压缩/写入及可合并统计；若按同步点拆分，必须证明状态充分、跨块调用栈/周期/序号正确，不可只找一个同步包就开始独立解码。

[OpenCSD 官方编程指南](https://github.com/Linaro/OpenCSD/blob/master/decoder/docs/prog_guide/prog_guide_main.md) 说明解码配置、映像访问与通用范围输出；当前仓库保留1.8.3实现。先复用并测量现有版本，升级库或自研特化解码器应单独做差分验收。

## 分阶段验收建议

| 阶段 | 交付内容 | 建议目标（尚未验证） |
|---|---|---|
| A | 固定F103/H743输入与当前引擎，补CPU、I/O字节、RSS、回调/序列化分项；纯sink模式只作性能诊断 | 建立可复测基准，不能将丢弃输出的耗时作为完整产品成绩 |
| B | C++回调直连builder，减少中间落盘，保持完整查询能力 | F103大样本完整离线API先争取≤10秒；H743独立比较 |
| C | C++索引/查询/发布融合，缓存静态映像，分页/多级视图 | 同一F103输入进一步争取≤5秒；约200ms级常用区间查询目标，需报告分位数和最坏值 |
| D | 有界持续流水线、增量视图、持续采集配合 | 持续处理超过实际输入速率，队列无长期增长；固定窗口/时长验证零丢数并实测Ozone对照 |

目标是分阶段去留门槛，不是预计收益或工期承诺。不能用减少功能、缩短窗口、降低目标频率或丢弃质量信息达标。

差分基准至少包含旧F103小输入、固定F103大输入、H743大输入、初始化/中断/异常返回、IT未知、截断尾包、失同步/overflow和失败采集。除summary外，逐序号比较PC、执行状态、调用路径/边界、周期锚点，验证默认图、区间查询、导航和导出；内部ID不同可以规范化。保持unknown/gap等真实语义，不把执行序号转换为伪造的逐指令精确时间。

使用相同主机、原始输入/ELF/配置SHA、Release编译、串行基准；冷启动与热缓存分组，至少3次完整重建报告全部结果，稳态/尾延迟另增加足够样本。原始输入、完整持久化和默认视图都纳入同一计时终点。故障注入验证取消、磁盘满、进程退出、输入变化时不发布完整manifest。源码通过后再验证冻结EXE及真实Web E2E。

本轮只形成设计和更新ZL-006证据；问题仍为“部分解决”，C++融合实现、优化收益和Ozone同条件对照均未完成。

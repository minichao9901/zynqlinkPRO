# JTAG IDDR 相位与采样窗口

本轮将 JTAG TDO 输入固定接入 OPPOSITE_EDGE IDDR。默认 `JTAG_TIMING[0]=0` 使用 Q2；bit0=1 使用 Q1。bit4 独立选择前一 DR 位窗口，厂商命令 `0x89` 保留四种模式 0、1、16、17 的查询/手动设置。两条路径都经过输入寄存器，不再旁路到裸引脚。

## 为什么仅切 Q2 不够

以 FCLK 周期 P、稳态 TCK 周期 2P 为例，`jtag_shift` 在准备拉低 TCK 的 FCLK 上升沿收取 DR 数据。该时刻取得的 Q2 来自前半个 FCLK 的下降沿，Q1 则来自前一个 FCLK 上升沿。因此 Q2 和 Q1 都比裸引脚取值更早；对于迟到的 TDO，必须同时检查采样位窗口。

| 模式 | 输入 | DR 窗口 | 理想返回延迟窗口，忽略建立/保持裕量 |
| --- | --- | --- | --- |
| 0 | IDDR Q2 | 当前位 | 0…1.5P |
| 1 | IDDR Q1 | 当前位 | 0…P |
| 16 | IDDR Q2 | 前一位 | 1.5P…3.5P |
| 17 | IDDR Q1 | 前一位 | P…3P |

这里的返回延迟包含 TCK 输出到目标、目标 TDO 更新、返回连线和输入路径。边界处仍需实际建立/保持裕量，不能仅凭 IDCODE 偶尔正确就选择该相位。

DR 帧固定多移两位：在 TDI 请求前填充两个无关位，使 UPDATE 时目标移位寄存器中的请求值保持正确。第一个额外时钟可收齐延迟的最后一个有效输出位，第二个才退出 SHIFT_DR，避免 TDO 输出使能过早撤销。保护时钟不会创建第二次 AP 访问；稳态仍是每个 AP 字一次 DR 扫描。

raw JTAG Sequence 不额外增加用户要求的 TCK 数。它使用较慢的扫描时钟，并在 TCK 上升前收取寄存后的 TDO，以保留 TMS=1、立即退出 SHIFT 时的末位。IR/TAP 导航同样使用较慢的时钟；缓存命中后的 DR 数据路径保持请求的高速时钟。

## 校准与测试修正

自动校准先在低速保存 AP CSW、TAR 和 DP SELECT 的软件影子，并读取只读 CPUID 作为基准。随后检查 IDCODE、CSW、TAR 多组图案读回及 CPUID，最后在低速恢复 CSW、TAR、SELECT。DPv0 的 SELECT 不依赖读回。校准不写目标内存，不执行 DRW 写；错误状态通过 JTAG CTRL/STAT 的 W1C 字段清除。四种模式均失败才允许按实际 FCLK 下降重试；已移除 43–52 MHz 请求的固定降频表。该校准目前仍可能漏过边缘相位，不能替代随机块读验收。

此前临时校准注释称读写 CSW，实际请求 `0x0f/0x0d` 在 bank0 访问 DRW，可能触及目标内存，现已修正。此前 `tools/jtag_speed_matrix.py` 还给 CMSIS-DAP Transfer 头部多插入了一个字节，导致请求误解码，旧矩阵不能直接作为相位根因的证据。修正后重新验收，并记录实际 FCLK/TCK 与采样模式。

## 仿真证据

`tools/run_jtag_timing_sweep.py` 使用完整双 TAP 模型，并按 IDDR Q1/Q2 的真实时钟边沿注册输入，覆盖 IDCODE、posted AP 读、AP 写以及 DP/AP IR 切换。

本轮 9 档 FCLK 周期 × 5 档 TDO 返回延迟 × 4 种模式，共 180 个组合。返回延迟为 12/16/20/24/28 ns，FCLK 周期为 8.333/9.091/9.615/10/11.111/11.628/12.5/14.925/16.667 ns。每个 FCLK×延迟组合至少有一个模式通过，详细结果为 `results/jtag/iddr_timing_sweep.json`。这表示可校准窗口覆盖，不表示每种固定模式都适用于全部延迟。

`tools/test_jtag_rtl.py` 进一步覆盖 Q2、Q2 前一位、Q1 前一位的自主 HSS 与 RTT 完整路径、DDR 提交前不更新 RTT RdOff、错误检查失败不发布采样包，以及 raw 扫描最后一位的输出使能撤销场景。`tools/test_probe_host.py` 对生产校准 C 代码检查四相位选择、TAR 图案与 CPUID 验证、SELECT/CSW/TAR/时钟恢复，并禁止目标内存写入。

旧 bit 加修正后的只读校准固件，其实板对照在 `results/jtag/before_iddr_checked.json`：请求 50 MHz 时实际 TCK 约 28.125 MHz，而请求 60 MHz 时实际约 60 MHz，说明验收必须核对实际频率。

## RTT/HSS 的 RTL 数据路径

两种传输共用 `probe_rtt_engine`、`probe_sample_engine`、`probe_stream_engine`，只在控制器内切换 SWD/JTAG 后端。JTAG 的 TAP、IR 缓存、DP/AP 访问、WAIT 重试、posted-read 结果回收和包边界错误检查由 `jtag_core` 实现。采样周期、跳点计数、RTT 环形缓冲读写位置、1 KiB 边界拆分和数据打包均由 RTL 实现；完整包经 AXI CDMA 搬入 DDR，再交 USB 控制器提交。PS 负责会话配置、启停、DMA 描述和 USB 队列，不逐字访问 AP，也不逐点组包。连接阶段的软件相位校准不属于采样热路径。

## superlinkPRO 源码对照

参考目录为 `E:/superlinkPRO/firmware/application_5301/src`。本轮逐段检查以下实际调用路径：

- `dap/JTAG_DP/JTAG_DP.c` 的 `JTAG_Read/Write` 调用 `JTAG_Read/Write_Slow`；45 MHz 汇编用于 `JTAG_Sequence`。不能把汇编文件名称当作普通 JTAG 块读的实测频率。
- `dap/JTAG_DP/JTAG_DP_GPIO_Slow.c` 的 ACK 在拉高 TCK 后采样，读数据在低电平等待后、拉高前采样。TDI 在拉低 TCK 前设置。非 OK ACK 提前退出 DR，正常请求使用 35 位加链上 bypass。
- `dap/DAP.c` 的 TransferBlock 先 prime，连续 AP 读每次取回上一笔，最后切 DP RDBUFF 收尾；RDBUFF 不作为可反复读取的 AP 结果缓存。
- `scope/scope_sampler.c` 的单字优化为固定地址 posted-read 流水，包尾用额外一次 pipe read 回填未决样本。其后端分派是 ARM SWD 与 RISC-V JTAG；这份代码不能作为 ARM JTAG HSS 已验证的依据。

参考中的缓存和流水语义保留，但这里的稳态调度与处理实现在 RTL，不能移植 MCU 轮询热路径。JTAG RDBUFF 的读零语义已加入仿真模型：包边界 CTRL/STAT 检查消耗的未决 AP 结果必须由 RTL 缓存，下一次前端访问先归还该结果，否则会在 HSS 数据中插入零。完整路径三种相位的仿真已通过。

## HSS 750 kHz 瓶颈定位

为区分“USB/PS 提交”与“PL 每样本访问预算”，把 HSS 输出切到丢弃模式（仅保留 PL 采样与跳点计数，`probe_stream.c` 的 `discard` 会话位），同一条 bit/ELF、60 MHz TCK：

| 周期 ticks | 请求速率 | 丢弃模式实际 | 丢弃跳点 | 回复模式实际 | 回复跳点 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 96 | 250 kHz | – | – | 250.0 kHz | 0.00% |
| 48 | 500 kHz | – | – | 496.0 kHz | 0.79% |
| 40 | 595 kHz | 595.2 kHz | 0.79% | – | – |
| 36 | 667 kHz | 656.2 kHz | 1.57% | – | – |
| 32 | 750 kHz | 375.0 kHz | 50.0% | 39.5 kHz | 94.74% |
| 28 | 857 kHz | 428.6 kHz | 50.0% | – | – |
| 24 | 1 MHz | 571.4 kHz | 42.9% | 39.4 kHz | 96.06% |

结论：

- **PL 侧**在 500–667 kHz 只丢 0.8–1.6%，到 750 kHz 才掉到 50%，即每样本扫描预算约等于 750 kHz 周期（60 MHz TCK 下约 1.3 µs）；这是采样 35 位 AP 访问加调度开销的真实成本。
- **回复路径**在 750 kHz 从 375 kHz 进一步塌到 39.5 kHz，比 PL 上限低一个数量级，且 750 kHz/857 kHz/1 MHz 都收敛到同一个约 39.5 kHz。恒定值说明不是带宽不足，而是提交侧进入了“大部分时间停住、偶尔推进”的节流/停顿模式，与请求速率无关。
- 因此 750 kHz 以上是**两个独立瓶颈**：PL 访问预算（~500–667 kHz 有效）与回复/提交路径（~39.5 kHz 塌陷）。500 kHz 时两者都不构成问题（0.79% 跳点），与 `hss_reply_long.json` 的 6 秒长测一致（496.0 kHz，跳点 0.79%，计数严格有序，错误 0）。

### 回复路径塌陷的定位

`hss_reply_checked.json` 中每档的提交计数器（`m0/final` 第 8 项为 DMA 提交次数，第 3、4 项为产出与跳点数）给出每次提交携带的样本数：

| 请求速率 | 产出样本 | 跳点 | 提交次数 | 每包样本数 | 提交速率 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 250 kHz | 500454 | 0 | 4549 | 110 | 2275 /s |
| 500 kHz | 1118459 | 8950 | 17899 | 62.5 | 8950 /s |
| 750 kHz | 93996 | 1597124 | 88943 | **1.05** | 40429 /s |
| 1 MHz | 90231 | 2164596 | 88847 | **1.01** | 40400 /s |

750 kHz 和 1 MHz 的提交速率都停在约 40.4k 次/秒，对应每次提交约 24.7 µs 的固定成本。也就是说：**每包样本数从 110 退化到 62.5、再到 1.05，包完全失去聚合**；提交次数撞上约 40k/s 的固定成本墙后，PL 只能丢弃其余样本，于是有效速率被钉在 39.5 kHz，与请求速率无关。

要恢复 750 kHz，先要让 RTL 侧保持在接近 256 样本（1 KiB）的包粒度，而不是每个样本提交一次；再降低单次提交成本。两处都在 RTL 打包与 PS 提交路径内，不影响 ≤500 kHz 的已验证行为。

未完成：包聚合退化的触发条件（每次跳点是否会提前结束当前包，或提交阈值随 tick 周期缩放）尚未定位；PL 每样本访问预算（约 1.3 µs）也没有继续压缩。

## JTAG 块访问的每字开销

验收脚本给出的 1.2 MB/s 是测量方式造成的：它对每 1 KiB 先发一次 `address()`（SELECT+CSW+TAR），再发一次块读，全部串行等回应，属于 USB 往返限制。用自增 TAR、每 1 KiB 一次请求、depth=8 流水重测（`tools/jtag_block_bench.py`，同板同 harness）：

| TCK | JTAG 读 | JTAG 写 | SWD 读 | SWD 写 |
| ---: | ---: | ---: | ---: | ---: |
| 30 MHz | 2.29 MB/s | 2.01 MB/s | 2.27 MB/s | 2.15 MB/s |
| 60 MHz | 2.31 MB/s | 2.20 MB/s | 4.13 MB/s | 2.98 MB/s |

换算成每字时间（4 字节/字）后能看出形状：

| TCK | MB/s | µs/字 | 34 位扫描本身 |
| ---: | ---: | ---: | ---: |
| 1 MHz | 0.080 | 50.0 | 34 µs |
| 10 MHz | 0.790 | 5.06 | 3.4 µs |
| 30 MHz | 2.29 | 1.75 | 1.13 µs |
| 60 MHz | 2.31 | 1.73 | 0.57 µs |

低速端与扫描时间吻合（1 MHz 时 50 µs/字 ≈ 34 µs 扫描 + 开销），说明扫描链路本身正常；**到 30 MHz 以后撞上一个约 1.73 µs/字的硬地板**，TCK 再快也不涨——这就是 30 和 60 MHz 吞吐相同的原因。

固件内置的 MET_PACKET_READ 计时把整笔开销拆开（64 包 × 65536 字节，60 MHz）：

| 项 | JTAG | SWD |
| --- | ---: | ---: |
| PL packet engine | **26.44 ms**（1.61 µs/字） | **12.94 ms**（0.79 µs/字） |
| DMA download | 0.45 ms | 0.46 ms |
| USB submit | 0.18 ms | 0.18 ms |

配对 `dbg_pkt_taken` / `dbg_pkt_fallback`（读法见 `tools/read_probe_counters.tcl`）为 5262 / 0：块传输确实走 PL packet engine，没有回落到 PS 逐字路径；`dap_transfer_block_engine` 也是 `ENABLE_CHAIN=1`，仿真里 16 字只用 18 次 DR 扫描，所以不是“每字多扫一遍”。

已排除的因素：采样相位（强制 mode 0 与 mode 17 在 30 MHz 都是 2.27/2.29 MB/s）、DMA 与 USB 提交（合计 <3%）、PL 回落（fallback=0）。结论是 **JTAG 每字有约 1.0–1.2 µs 的固定开销，落在 PL packet engine 与 `jtag_core` 的握手/状态机里，与扫描时间无关**；SWD 同一路径几乎没有这项开销（0.79 µs/字 ≈ 46 个 SWCLK）。

下一步应做逐周期分解：在 `fpga/sim/tb_jtag_pipeline.sv` 里对 `jtag_core` 每个状态计 FCLK 周期，直接指出这 ~1.1 µs 花在哪个状态；本轮的板上测量只能定位到“PL 引擎内部、与 TCK 无关”。

## 结论：瓶颈是目标 DP 的 AP 周转，不是 RTL

上面的推断已被逐状态计数推翻。`jtag_core` 新增三个统计计数器（`stat_cycles` 累计 PHY 等待周期、`stat_bits` 累计扫描位数、`stat_transfers` 累计扫描次数，CSR `0xC0/0xC4/0xC8`，由 vendor `0x89` 回读），比值 `stat_cycles/(2*stat_bits)` 直接给出 `half_delay+1`。仿真标定为 half_delay=0 时 1.052、half_delay=1 时 2.028，可无歧义区分“真 60 MHz”和“半速”。

实板读数（块读，256 字×32 包）：

| 请求 TCK | bits/scan | cycles/(2·bits) | **scans/word** | MB/s |
| ---: | ---: | ---: | ---: | ---: |
| 30 MHz | 42.8 | 1.03 | **1.04** | 2.26 |
| 40 MHz | 42.8 | 1.03 | 1.04 | 2.42 |
| 45 MHz | 42.8 | 1.03 | 1.04 | **2.53** |
| 50 MHz | 42.8 | 1.03 | 1.04 | 2.50 |
| 55 MHz | 43.4 | 1.02 | **2.04** | 2.07 |
| 60 MHz | 43.4 | 1.02 | **2.04** | 2.30 |

三点结论：

1. **TCK 确实是 60 MHz**（比值 1.02，不是半速），43 位帧也和设计一致，所以扫描链路和 RTL 都没有问题。`jtag_core` 单独仿真也只要 92 个 FCLK 周期/字，与 1.04 次扫描/字吻合。
2. **50 MHz 以下每字只用 1.04 次扫描**，即流水完全生效；**55 MHz 以上变成 2.04 次**，多出来的一次是 `retries` 里的 WAIT 重试——目标 F103 的 JTAG-DP 来不及完成上一笔 AP 访问。
3. 重试把时钟提升的收益全部吃掉，还会略微下降：**45 MHz 是最佳点 2.53 MB/s**，60 MHz 只有 2.30 MB/s。之前“30 和 60 MHz 一样快”“1.73 µs/字硬地板”的真正原因是这个重试，不是 PL 引擎的固定开销。

由此，JTAG 块访问的正确上限是 ~45–50 MHz，而不是 60 MHz。目标 DP 的 AP 周转时间落在 0.81–0.86 µs 之间（50 MHz 时单次扫描 0.86 µs 够用，52.9 MHz 时 0.81 µs 不够）。加 `idle_cycles`（0/4/8/16/24）无效，说明瓶颈不是帧尾空闲时长；换采样相位（mode 0 与 17 在 30 MHz 都是 1.04 次/字）也无关。

剩余开销：45 MHz 下 1.58 µs/字中约 0.96 µs 是扫描，约 0.6 µs 是引擎与握手，这一项仍可优化，但已不是主因。

之前的 vendor `0x89` TCK 计数器读数是解析偏移错位（应为 `r[3:7]/r[7:11]/r[11:15]`，当时用了 `r[4:8]`），计数器本身没有问题；已改为返回两个扫描统计量。

### LA 独立校验（CH0=TCK、CH1=TMS）

用 Kingst MIPI16、500 MS/s、5 ms 窗口、阈值 1.65 V，在块读突发期间抓 TCK/TMS（`tools/la/la_jtag_scans.py`，采集用 `E:\zynqlinkPRO\tools\la\la_capture_export.py`）：

| 项目 | 实测 |
| --- | ---: |
| 窗口 | 5.000 ms |
| TCK 上升沿 | 141957 |
| 沿速率 | 28.39 M/s |
| 扫描内 TCK 周期中位数 | 28.0 ns → 35.71 MHz |
| 包与包之间的间隙 | 中位 17.2 µs |
| **每字 TCK 脉冲** | **44.8** |

44.8 与计数器的预测完全吻合：43 位 × 1.04 次扫描/字 = 44.7。也就是说 **LA 与 RTL 计数器是同一个量的两种独立测法，互相验证通过**，因此计数器在 55–60 MHz 读到的 2.04 次/字（≈ 88 脉冲/字）可以直接采信——重试确实存在，且整整多出一倍扫描。

一个额外的实测发现：**仅把探头接到 TCK/TMS 上，闭环校准的最高可用 TCK 就从 60 MHz 掉到约 35 MHz**（FCLK 120 → 69.2，换回 15:44 的旧 bit 也一样）。TDO 没有被探头加载，说明是 TCK 边沿被探头电容稍微推迟、目标 TDO 相应后移，把本来就窄的采样窗口挤掉了。这解释了为什么 50–60 MHz 一直很脆，也说明后续该做的是**加宽 TDO 采样余量**，而不是去调重试逻辑。

带探头时 60 MHz 请求会落到 36 MHz；摘掉探头后 60 MHz 请求恢复到 60 MHz TCK。第 1/10/30 MHz 验收在带探头时仍然全部通过。

## 实测吞吐与理论差

验收脚本里的 1.2–1.25 MB/s 不能当线速：它对每 1 KiB 先发一次 `address()`（SELECT+CSW+TAR）再发一次块读，属 USB 往返受限。用自增 TAR、每 1 KiB 一次请求、depth=8 测真实流水：

| TCK | 流式块读 | 帧长 | 帧受限上限 | AP 周转上限 |
| ---: | ---: | ---: | ---: | ---: |
| 30 MHz | 2.29 MB/s | 43 位 | 2.68 MB/s | 4.8 MB/s |
| 31 MHz（降级） | 2.28 MB/s | 43 位 | 2.77 MB/s | 4.8 MB/s |
| 60 MHz | 2.29 MB/s | 43 位 | 5.6 MB/s（但 2.04 次/字重试把它压回 2.8） | 4.8 MB/s |

- 30 MHz 下实测是帧受限上限的 **85%**。差距分布：`late_return` 的 2 位填充 4.9%、二 TAP 链上 1 位 bypass 2.4%、每字 6 个 FCLK 状态机周期约 4%、包引擎与 USB 约 3%，基本对得上。
- 30 MHz 下 43 位帧 = 1.43 µs，比目标 DP 的 AP 周转（约 0.83 µs）**长**，所以 JTAG 是帧受限；60 MHz 下帧缩短到 0.72 µs，却又短于 AP 周转，触发 WAIT 重试变成 2.04 次/字，净吞吐回到 2.8 MB/s 上限。这就是"提频不提速"的机制。
- 想真正上到 AP 上限（约 4.8 MB/s），需要 TCK ≥ 52 MHz 且**不触发重试**；SWD 60 MHz 的 4.13 MB/s 正是已经贴在 AP 上限上。

## RTT / HSS 实测（JTAG）

| 项目 | 条件 | 结果 |
| --- | --- | --- |
| RTT 正向 | 30 MHz TCK，512 B 块 | **2.04 MB/s**，序列完全一致，错误 0 |
| HSS | 30 MHz TCK | 250 kHz 稳定（跳点 0.79%）；375 kHz 起塌到约 40 kHz（跳点 89–93%） |
| HSS | 60 MHz TCK（重构前） | 500 kHz 稳定（0.79%）；750 kHz 起塌到 39.5 kHz |

HSS 在 30 MHz 下可用上限是 250 kHz，在 60 MHz 下是 500 kHz，塌陷点都落在约 40 kHz 那堵"每次提交 1 个样本、约 24.7 µs/次"的墙上，与之前定位一致。

## WAIT 重试的真正原因：帧尾空闲为 0

上一节猜测是目标 AP 周转来不及。加了专用 CSR（`0xD0`，并可经 vendor `0x8A` 从主机写）后可以逐档扫 `idle_cycles`，结论推翻了这个猜测——**原因是帧尾 Run-Test/Idle TCK 为 0**，不是 AP 周转：

| idle | scans/word | bits/scan | MB/s（60 MHz，目标运行中） |
| ---: | ---: | ---: | ---: |
| 0 | 2.03 | 42.4 | 2.261 |
| 1 | **1.04** | 42.8 | 2.293 |
| 4 | 1.51 | 46.1 | 2.918（未做数据校验） |
| 8 | 1.04 | 49.6 | 2.006 |
| 15 | 1.04 | 56.4 | 1.776 |

`bits/scan` 随 idle 线性增长（`43+idle`），证明寄存器确实进了 RTL。**只要 idle ≥ 1，背靠背扫描就不再被 WAIT 打断**，重试消失。

注意寄存器写入受 `!core_busy` 限制：`PORT_JTAG_SETUP` 里的写经常落不下去，主机用 vendor `0x8A` 在空闲时写才可靠。

## 60 MHz 仍然不可用，JTAG 上限钉到 32 MHz

idle 修掉之后重试不再是瓶颈，但 60 MHz 的**数据**仍不可靠，而且**不确定**：同一份固件多次运行，校准有时拒绝 60 MHz（降级到 30 MHz 后一切正常），有时接受（随后 4096 字节随机读 8/8 全错）。目标运行态下把 idle 取 1/4/8 实测都是 8/8 错，说明与帧尾空闲无关。

这种"有时对有时错"比明确拒绝更危险，所以 `DAP_MAX_JTAG_TCK_HZ` 固定为 32 MHz：超过的请求一律按 32 MHz（实际 31.03 MHz）服务。改后逐档验证确定通过：

| 请求 | 实际 TCK | 校验 |
| ---: | ---: | --- |
| 1 MHz | 1.00 | 107940 字节全对 |
| 10 MHz | 10.00 | 全对 |
| 30 MHz | 30.00 | 全对 |
| 40 / 50 / 60 MHz | 31.03 | 全对 |

上限用 `jtag_block_bench` 复测：读 2.32 MB/s、写 1.86 MB/s @31.03 MHz。

把上限解开的唯一途径是加宽采样余量（IDELAY 或接上 `sample_tick`）。由于重试已经被 idle 消除，一旦 60 MHz 的捕获可靠，吞吐就能接近帧受限的 5 MB/s，而不是被重试压回 2.8。
## 仿真定位：不是相位选错，是 TCK 输出延迟

给 `tb_jtag_timing` 加了 `tckout` 参数（TCK/TMS/TDI 离开 fabric 的延迟，默认 0）。之前的模型让目标在 FCLK 沿瞬间就响应，所以仿真一直比实板乐观。

60 MHz（`half_q=65536`，FCLK 120 MHz）扫描结果：

| tckout | TDO 往返 ≤22 ns | TDO 往返 ≥24 ns |
| ---: | --- | --- |
| 0 ns | mode 16/17 通过 | mode 16 通过、17 失败 |
| 7 ns | mode 16 通过 | **四个模式全部失败** |

30 MHz（`half_q=131072`）在 tckout=7、往返 22–26 ns 时始终至少有一个模式通过。

结论：**真实 TDO 往返约 24 ns**，而 60 MHz 的位周期只有 16.7 ns；再叠加 TCK 输出延迟，60 MHz 在物理上不可捕获。重构前能过，是因为当时 TCK 输出路径更浅，余量刚好为正；新发生器加深了这条路径（`half_q` 多路选择 + 40 位计数器 → `tick` → `tck`），把它推成负数。这也解释了为什么加一根 LA 探头就能把可用频率从 60 拉到 35 MHz。

## 更正：IOB 打包不是修法，方向是反的

原本打算在 mux 之后加一级输出寄存器并 `IOB TRUE`。用仿真实测这个方向，结论相反：60 MHz、TDO 往返 24–26 ns 时，**TCK 输出延迟越小通过组合越多**：

| tckout | 通过组合 |
| ---: | ---: |
| 0 ns | 3 / 8 |
| 2 ns | 2 / 8 |
| 5 ns | 1 / 8 |
| 7 ns | 0 / 8 |

原因是采样时刻固定在内部 tick 上：TCK 引脚越晚翻转，目标就越晚送出 TDO，采样余量越小。而 IOB 打包必须先把 mux 的结果打一拍（因为端口前有三选一 mux），这一拍就是 8.33 ns，比现在 SLICE 到焊盘的 5–7 ns 还多。**加一级寄存器净效果是变差。**

而且即使 tckout=0、往返 24 ns，也只有 3/8 组合能过——本身就处在边缘。所以：

- **32 MHz 上限保持不变**（确定性、数据核对通过）；
- 想把上限抬到 50–60 MHz，需要的不是布局技巧，而是**亚周期可调的采样时刻**：在 PL 里加一个相位可移的采样时钟（MMCM 或 clk_wiz，把采样沿挪到 TCK 引脚翻转前 1–2 ns），或者接受更低的速率。

这一条先按"限制"记着，不作为本轮实现目标。
## 与重构前的同口径对比

重构前基线：bit 17:54 / 固件 17:56，最高可用 TCK 60 MHz。现在：32 MHz 上限，实际最高 31.03 MHz。全部用同一批脚本重测。

| 指标 | 重构前（60 MHz） | 现在（31 MHz） | 变化 |
| --- | ---: | ---: | ---: |
| 块读流式（不校验数据） | 2.193 MB/s | 2.27 MB/s（3 次中位） | +3% |
| 块写流式 | 2.196 MB/s | 2.13 MB/s（3 次中位） | −3% |
| 验收吞吐（校验数据） | 1.230 MB/s | 1.08 MB/s（3 次，1.077–1.091） | −12% |
| RTT（校验序列） | 2.391 MB/s | 2.037 MB/s | −15% |
| HSS 稳定点 | 496 kHz | 250 kHz | −50% |

原因拆得开：

1. **每拍效率是提升的。** 重构前 60 MHz 下核心要 **2.04 次扫描/字**（`idle=0` 导致每字一次 WAIT 重试）；现在 `idle≥1` 后是 **1.04 次/字**。也就是说同样拍数下现在的有效带宽更高。
2. **最高频点腰斩。** 60 MHz 需要 TCK 输出延迟 ≈0–2 ns，而当前实现约 7 ns；仿真实测 60 MHz、TDO 往返 24 ns 时，tckout 从 0→7 ns 会把通过组合从 3/8 降到 0/8。这是硬件参数，不是策略选择。
3. **块读流式基本打平**：重构前用 2 倍时钟但多扫一遍，两个效应正好抵消。
4. **RTT/HSS 明显下降**：它们基本随频点线性缩放，1.04 vs 2.04 次扫描省下的 5% 抵不过 2 倍的时钟损失。
5. **可信度不同。** 重构前的 60 MHz 是边缘状态：接上 LA 探头就掉到 35 MHz，换一次布局可用频点集合就变。现在的 31 MHz 是校准链式验证过、可复现、数据核对通过的。

结论：**最大速度确实下降了（RTT −15%、HSS −50%），但每拍效率提升、且结果从"看运气"变成"确定"**。要把绝对值涨回去，唯一有效的路径是相位可移采样时钟，把 TCK 输出延迟的影响消掉；那一步做完，60 MHz 下 1.04 次/字可以直接换成约 5 MB/s 的帧受限上限。
## 上限的真正决定因素：FCLK 窗口，不是 TCK

把上限临时抬到 50 MHz 逐个试（40/45/50 MHz 请求在 FCLK 80/90/100 上）：

| 请求 | 目标 FCLK | 校准结果 | 实际服务 |
| ---: | ---: | --- | ---: |
| 35 MHz | 70 | 拒绝 | 27.27 |
| 40 MHz | 80 | 拒绝 | 31.03 |
| 45 MHz | 90 | 拒绝 | 28.12 |
| 50 MHz | 100 | 拒绝 | 31.03 |

加"链式探针重试 3 次"后结论不变，说明不是时钟切换后的抖动，是这些 FCLK 上真的读不对。

结合仿真：45 MHz（FCLK 90、半周期整数 1.0、TDO 往返 22–26 ns）在 tckout=0 和 7 ns 下都是 6/12 通过，即**仿真认为应该可用**。板上却是拒绝。差异只剩一个解释：**可用与否由 FCLK 的具体取值决定，不是由 TCK 比例决定**。目前观测到的规律：

- **可用**：FCLK 62.07（TCK 31.03）、FCLK 120（TCK 60，但只在 4 个相位里部分可用）
- **不可用**：FCLK 70 / 80 / 90 / 100（TCK 35–50）

重构前 FCLK 90 是好的（45 MHz、2.53 MB/s 就发生在那里），重构后 TCK 输出延迟多了约 2–3 ns，把这个窗口推走了。所以"恢复 45 MHz"不是调比例，而是要把采样相位整体挪回 2–3 ns——也就是相位可移采样时钟那件事。
## 试过并否掉：FCLK 粒度的采样偏移

参考 HFLink 的做法（`REG_TIMING_SIMPLING` 独立采样比较值 + 延迟链），把 `swj_clk_gen` 里早就留好但一直接 0 的 `sample_off` 接了出来：

- `jtag_shift` 新增 `sample_off` 端口，非 `0xFFFF` 时在**上升沿之后第 N 个 FCLK** 采 TDO，`0xFFFF` 保持原来的"下降沿采样"；
- `jtag_core` 透传，`swd_controller` 新增 CSR `0xD4`，复位值 `0xFFFF`；
- `tb_jtag_timing` 增加 `+sampleoff=`，`run_jtag_timing_sweep.py` 增加 `--sampleoff`。

仿真结果（tckout=7、往返 22–26 ns、四个相位）：

| 配置 | legacy（下降沿） | 上升沿采 | 上升沿+1 |
| --- | ---: | ---: | ---: |
| 45 MHz，FCLK 90，半周期 1.0 | **6/12** | 0/12 | – |
| 45 MHz，FCLK 120，半周期 1.333 | **6/12** | 1/12 | 0/12 |
| 50 MHz，FCLK 100，半周期 1.0 | **4/12** | 0/12 | – |

**粗调无效，而且比现状更差。** 原因是纯算术的：45–60 MHz 时一个 bit 周期只有 11–17 ns，而这里最小可调步长是 **一个 FCLK = 8.33 ns**，半周期本身又只有 1.0–1.33 个 FCLK——根本没有"中间采样点"可放。这个旋钮只在半周期 ≥2 个 FCLK（≤31 MHz，本来就正常）时才有意义。

所以 HFLink 的三层里，我们缺的是**最细的那层**：它的 IODELAY 是亚纳秒级（8 位 DLYSTEP），而 `REG_TIMING_SIMPLING` 和延迟链都只是 FCLK 粒度。要挪 2–3 ns，只能上 `IDELAYE2`（7 系列约 78 ps/tap）。

保留代码：`sample_off` 默认 `0xFFFF` 等于旧行为，全部回归（core + 三个 pipeline）通过，不影响现有验收。
## 实测频点地图（绕过调度器强制设频）

校准的降级会掩盖真相（每个请求都被先降级），所以加了 vendor `0x8B`：直接把 FCLK 设成 `2*TCK`、写半周期，**不走上限、不走校准**。这样能单独测某个频点。每档测 4 个相位 + 64 字节写读，再对能过的档做 4 KiB × 8 次校验：

| 目标 TCK | FCLK | mode 0 | mode 1 | mode 16 | mode 17 |
| ---: | ---: | --- | --- | --- | --- |
| 30.00 | 60 | **ok** | ERR | ERR | **ok** |
| 39.13 | 78.26 | ERR | ERR | ERR | ERR |
| 45.00 | 90.00 | ERR | ERR | ERR | ERR |
| 50.00 | 100.00 | ERR | ERR | ERR | ERR |
| 60.00 | 120 | ERR | ERR | 64 字节 ok | 64 字节 ok |

**60 MHz 的 64 字节通过是假象**：同样的 mode 16/17，4 KiB 随机块 8/8 次读回全错；而 30 MHz（mode 0）0/8 全对。

结论：

- 可用点只有 **FCLK 60（TCK 30）**，以及 **FCLK 120（TCK 60）在短传输上看起来可以、长传输必错**；
- **FCLK 78 / 90 / 100 四个相位全死**，与 TCK 比例无关——这是 FCLK 取值的窗口效应；
- 而且 FCLK 90 上连"半个 FCLK 的另一侧"（mode 1，Q1）也失败，说明**现有的半个周期粒度不足以找到好窗口**。

所以 45/50 MHz 不是"差一点点"，是整块落在窗口外；把 60 MHz 做到可靠也不是调相位能解决的（16/17 已经是能过 64 字节的最好相位，长传输仍必错）。

17:54 那版 bit 已被后续构建覆盖，所以在 tag `902e228` 上开了独立 worktree 重建（`git worktree add ... probe-jtag-baseline-20261027`，用 `fpga/build_dma.tcl` 全量构建，23:24 时序通过），烧录后逐档实测。

| ---: | ---: | ---: | ---: | --- |

- 读：33.33 / 31.03 = 1.074，实测差 7.5%，即**每拍持平**；
- 写：差 17%，即每拍约慢 10%，这是真实的退步；
- 区别在于当前版本对 50/60 请求**降级到验证过的 31.03 并保证数据正确**，而不是跑错误数据。

## RTT / HSS 在重构前基线上无法用 JTAG 测量

`probe_stream.c` 里 RTT/HSS 会话配置（`action 0x31 act 7`）有这样一道门禁：

```c
else if (req[1] < 10 || mode == 2 || pending_len || rtt_pl_running || dma_pending)
    rc = -7;
```

`mode == 2` 正是 JTAG 传输，也就是**这一版的固件在 JTAG 下直接拒绝配置 RTT/HSS 会话**（`-7`）。实测在任何速率都返回该错误。

结论：之前引用的"重构前 RTT 2.39 MB/s、HSS 496 kHz"**不可能是 JTAG 数据**（只能是 SWD 或另一版固件）。因此拿它们和当前 JTAG 的 RTT 2.037 MB/s、HSS 250 kHz 对比是不成立的，那组"RTT −15%、HSS −50%"的结论作废。

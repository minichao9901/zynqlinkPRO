# 流水线与块大小实验（2026-10-25 晚）

目标：验证“主机侧流水线”和“更大块”能把 60 MHz 下的读速从 OpenOCD 的 3.37 MB/s 拉到哪里。
方法：`tools/dap_pipeline_bench.py`，raw libusb 客户端；连续发多个 `0x06` 块读、再统一收响应，
与逐条“发一条收一条”对比。F103 HCLK=64 MHz，SRAM 0x20000000，数据只读不写。

## 结果

| 块大小 | 模式 | 60 MHz 读 | 50 MHz 读 |
|---|---|---:|---:|
| 770 字 | 顺序（≈OpenOCD） | 3.26 MB/s | — |
| 770 字 | 流水线 depth=4 | 4.13 MB/s | — |
| 770 字 | 流水线 depth=8 | **4.34 MB/s** | — |
| 1023 字 | 顺序 | 3.36–3.48 MB/s | 3.05 MB/s |
| 1023 字 | 流水线 depth=4 | 4.26 MB/s | — |
| 1023 字 | 流水线 depth=8 | **4.46 MB/s** | **3.76 MB/s** |

写方向：顺序 4.10 MB/s，流水线 4.12 MB/s（1022 字/包）——**写没有收益**，
因为它的 IN 响应只有 4 字节，USB 延迟本来就藏得住。

数据一致性：连续两轮各 4 个流水线 1023 字读，4 个响应逐字节一致。

## 结论

1. **读的瓶颈确认是主机串行等待**：设备端 SWD 执行 770 字约 656 µs，
   对应上限约 4.7 MB/s；流水线 depth=8 实测 4.46 MB/s，已达到该上限的 ~95%。
2. **块大小收益很小**（770→1023 约 +3%，顺序模式 +2–6%），因为流水线已经把每块开销摊掉了。
3. **协议上限**：CMSIS-DAP 包 4096 B、带 DAP index 字节（`0x06 idx cntL cntH req`）时，
   读最大 1023 字（响应 3+4092=4095），写最大 1022 字（请求 5+4088=4093）。
   写 1023 字会得到 4097 B 的 OUT，被拆成 4096+1，多出的 1 字节会被当成一条新命令，
   现象是收到 1 字节 `ff` 响应——我的第一版测试就踩了这个坑。
4. **OpenOCD 侧要吃到这 30%**，需要让 `cmsis_dap` 驱动把多个块读排队（它已有
   `MAX_PENDING_REQUESTS=4` 和 async bulk，但内存读取路径是逐块等待的）。
   设备固件和 RTL 不用改。

## 复现

```powershell
python tools/dap_pipeline_bench.py --speed 60000 --words 1023 --loops 40 --depth 8 --output results/optimization/pipe_1023_d8.json
python tools/dap_pipeline_bench.py --speed 50000 --words 1023 --loops 40 --depth 8 --output results/optimization/pipe_1023_d8_50m.json
```

原始结果：`results/optimization/pipe_770_d4.json`、`pipe_770_d8.json`、
`pipe_1023_d4.json`、`pipe_1023_d8.json`、`pipe_1023_d8_50m.json`。
